# 传承文档格式规则

> **定位**：规范 `传承殿/**/*.md` 与未来 `.传承/**/*.md` 中所有文档的**结构与元数据**，使文档在人类阅读、链接引用、自动化校验三方面保持一致。
>
> **与命名规则的关系**：本文只约定**文档内容结构**，不重复约定文件命名（见《命名规则》一/二）。
>
> **与 AI 缺陷治理规则的关系**：本文档规定的内容会被《AI 缺陷治理规则》的「文档结构门禁」类门禁自动扫描。

## 一、文档分型（强约束）

传承文档按"读者意图"分为以下 6 型，**任一文档必须在元数据 `文档型` 字段中明确标注其一**，并按对应模板组织章节。**禁止混型**——同一篇文档既是「落地设计」又是「验收报告」属于违规。

| 文档型 | 读者意图 | 主要章节（参考） | 落点 |
|-------|---------|----------------|------|
| 落地设计 | 实施契约（开发前看） | 诉求与结论 / 现状事实 / 设计决策 / 契约定义 / 实施顺序 / 验收基线 / 风险 / 修订 | `落地设计-域/` |
| 验收报告 | 完工验证（交付后看） | 验收范围 / 验收方法 / 验收结果 / 遗留事项 / 复现命令 | `落地设计-域/`（与对应设计文档并列） |
| 设计原则 | 演进中的思考（可改） | 命题 / 现状 / 命题展开 / 反例 / 倾向 / 待证 | `设计原则-域/` |
| 已定契约 | 实现必须遵守的决策 | 状态版本 / 章节 | `已定契约-域/` |
| 治理档案 | 缺陷/变更/排查的盘点 | 时间锚 / 范围 / 方法 / 结论 / 表格 | 按治理物自身所属域安置（如 `缺陷清单.md` / `修订记录.md` / `维护文档.md` 均在 `传承殿/` 根） |
| 规则 | 跨项目的强约束 | 层级声明 / 章节 / 例外登记 | `rules/` |

## 二、文档头部元数据（强约束）

每篇文档**必须在第一行 `# 标题` 之前**包含如下 frontmatter 元数据块（YAML 风格），用 `---` 包裹。**缺一不可**：

```markdown
---
层级: 大道 | 天道            # 强约束二选一，对齐 rules/*.md 已有层级标注
文档型: <上节六型之一>        # 见第一节，强约束
版本: <语义版本，如 1.0>
域: <九根/域路径，或「全项目」>
状态: <草稿 | 讨论中 | 已定 | 已废>
更新: YYYY-MM-DD             # 最后一次实质修改日期
---
```

> **说明**：`层级` 与 `状态` 是该文档的强约束；`版本` 与 `域` 与 `更新` 是辅助元数据，便于人类快速识别。

### 例外

1. **`rules/*.md`**：保留现有「层级: 大道/天道」单一字段，**不强制六元数据块**（规则本身就是约定，不能用规则约束自身）。
2. **`修订记录.md` / `缺陷清单.md`**：治理档案的 `状态` 固定为「已废」或「已定」，**`文档型: 治理档案`**。
3. **`维护文档.md`**：维护文档作为项目「当前状态」权威源，`状态: 已定`、`更新` 字段每次维护时必改。

## 三、引用块约定

文档开头第一段块引用 `>` 是**文档定位**：

```
> 定位：<一句话讲清本文件是什么 / 给谁看 / 解决什么>
> 不解决什么：<显式排除的范围>
```

**禁止**：把引用块当成普通段落使用。

## 四、章节编号与跳转

1. **一级章节用 `##`**（`#` 只用于文档标题），与已有文档保持一致。
2. **章节编号用中文数字 + 半角点**（`一、`、`二·一、`、`二·一·二、`），不使用阿拉伯数字。
3. **章节标题要能独立成句**：章节本身在目录里是「标题树」，不是「段落开头」。
4. **每章可有可无的 `### 子节`**，但**禁止三级以上嵌套**（超过两级章节说明该拆文档）。

## 五、表格与代码块的约束

| 类型 | 约束 |
|------|------|
| 表格 | 表头与第一行数据必须完整，**不允许表头与表体分裂** |
| 代码块 | 必标语言（`rust`/`toml`/`bash`/`markdown`），**不允许无标记代码块** |
| 行内代码 | 仅用于文件名、字段名、函数名；**禁止用行内代码强调普通文字** |

## 六、引用与关联

1. **关联文档**用一句话写在元数据后、第一章前：「**关联**：`路径/文档.md` §章节、…」——给出**相对路径 + 章节锚点**，而不是「见前文」「详见上节」。
2. **历史补注 / 修订说明**用 `> **历史归档补注（YYYY-MM-DD）**：…` 块引用，放在文档开头元数据后、第一章前，**与现状描述明显分隔**。
3. **同一文档经历重大修订**：保留原文不动，在文档尾追加「## 修订记录」一节，注明日期与变更要点。**不删旧章节、不覆盖式重写**。

## 七、长度与可读性

1. **单文档 ≤ 1500 行**：超过则按"主文档 + 附录"拆开，附录文件以 `<原名>-附录-府/` 收容。
2. **段落 ≤ 8 行**：超过则拆段，避免滚动疲劳。
3. **每章结尾留 1~3 行「小结」**（可选）：用于文档内自检，让读者确认读到了关键信息。

## 八、与现有文件的迁移

1. **新增文档**必须按本文六型 + 元数据块写。
2. **现有文档**不强制立即迁移，但每次大改（`状态: 已定` 切换、`更新` 改动）时顺手补齐元数据；补齐时间与「修订记录」挂钩。
3. **`维护文档.md`** 作为项目「当前状态」权威源，单独维护，**不按本规则强约束**——它是元元数据，是规则的载体而非规则的服从者。

## 九、违反该规则的处置

1. **门禁扫描**：`rules/AI缺陷治理规则.md` 应新增「文档元数据完整门禁」（扫描 `传承殿/**/*.md`，要求每篇都含完整 frontmatter）。
2. **人工审查**：道祖终审阶段须检查新增文档是否合规；不合规的文档不进 `落地设计-域/`。
3. **历史文档豁免**：2026-09-11 前的存量文档享有 90 天豁免期，豁免期内不因缺元数据被门禁拦下；豁免期后逐步补齐。
