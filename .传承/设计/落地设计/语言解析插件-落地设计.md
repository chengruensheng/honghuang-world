# 通用语言解析插件架构

> **定位**：定义「知识图谱」第 2 阶段（符号层）的语言解析插件架构——引擎如何发现、调度、校验语言插件，插件如何以统一契约交出符号与边；使符号解析可跨语言扩展，而引擎自身不含任何语言名词。
> **不解决什么**：不定义坐标层机制（见 `坐标索引.md`）、不定义诊断规则（第 4 阶段）、不规定任一具体语言的解析算法。

**关联**：`.传承/图谱/知识图谱/坐标定义.json`（坐标层定义）、`.传承/图谱/知识图谱/坐标索引.md`（坐标层产出）、`传承殿/设计原则-域/完整架构蓝图.md` §5.2（六层职责）、`rules/命名规则.md`（层级命名约束）、`.传承/设计/落地设计/代码文档生成-落地设计.md`（下游：叙述层消费本层产出）

## 一、诉求与结论

### 诉求

第 1 阶段（坐标层）只回答"东西在哪"，不回答"东西引用了谁"。要让"过期 / 可清理"的判定成立，必须再叠一层**事实依赖**：符号定义、导入、实现、调用。而依赖提取天然是语言相关的——Rust 要解析 `use`/`impl`，前端要解析 `import`，二者的工具链毫无交集。

若把语言知识写进引擎，引擎就成了一堆 `if 语言 == "rust"` 的泥球，且每接一种语言都要改动引擎。

### 结论

拆成**三层职责**：引擎（语言无关的调度与合并）、契约（语言无关的数据协议）、插件（语言相关，每语言一个独立进程）。

引擎通过**两份 JSON 契约**与插件通信：插件用「清单协议」自述能解析什么、精度多高；用「产出协议」交出统一的符号与边。引擎永远不知道 Rust 是什么，只认契约。

### 与 `项目认知-府` 的边界

`项目认知-府` 已具备一个单语言、crate 级的「运行时世界态图谱」：tree-sitter 提取顶层 pub 符号，读 `Cargo.toml` 生成依赖边，经 `三态存储` 落到 `persistence.dir/认知三态/图谱.json`，供 agent 对话时注入上下文。它已有 285 行扫描器、94 行图谱模型、51 行查询与 371 行规则提炼。

两者产物**目标不同、生命周期不同**：

| 维度 | `项目认知-府`（现有） | 本设计（符号索引） |
|---|---|---|
| 服务对象 | 运行时 agent 对话 | 静态诊断（死代码 / 孤儿 / 漂移） |
| 生命周期 | 内存态，随进程生灭 | 仓库固化，随代码提交 |
| 存储性质 | `persistence.dir/`（**状态**，不入 git） | `.传承/图谱/知识图谱/`（**源**，入 git） |
| 粒度 | 顶层 pub 符号，够用即可 | 全量符号 + 文件 / 模块树 + 四类边 |
| 精度 | 线索级 | 必须可差分（ID 稳定 + 行号位置） |
| 语言 | 仅 Rust，硬编码 | 插件化，多语言 |

结论：**并存，不合并**。合并会让 `项目认知-府` 承担它不该承担的职责，并违反「源态二分」——静态索引产物必须入 git 才能跨会话差分，而 `persistence.dir/` 是 gitignore 的状态目录。

两者的共性只是底层 tree-sitter 接线。若日后重复成本变高，可再抽公共解析层；本设计不预先抽象。

## 三、设计决策

| # | 决策 | 选择 | 理由 |
|---|---|---|---|
| 1 | 引擎与语言的关系 | 引擎零语言名词 | 与坐标引擎的"零项目名词"同构；接新语言不改引擎 |
| 2 | 插件接入方式 | 独立进程 + JSON 协议 | Rust / Node / Python 运行时互不污染；插件可崩溃而不拖垮引擎 |
| 3 | 插件发现方式 | 显式登记，不扫目录 | 未登记即不启用，便于灰度；避免扫入意外目录 |
| 4 | 符号 ID 构成 | 只依赖源码结构，**不含行号** | 行号一变则 ID 漂移，差分诊断（对比两次索引）将失效 |
| 5 | 精度表达 | 能力矩阵 + 逐边置信度 | 不同工具精度差异巨大，诊断结论必须可分级采信 |
| 6 | 解析失败的处理 | 产出「悬空引用」而非丢弃 | 悬空正是"幽灵引用"诊断的原始素材 |
| 7 | 代码与数据的归属 | 数据落 `.传承/`，代码落项目区 | `.传承/` 按规范是"非代码的集合地"；代码须遵守"代码落园" |
| 8 | 首批语言 | 只做 Rust，契约按多语言设计 | 项目主体是 Rust，性价比最高；架构不为未接入语言付实现成本 |

## 四、契约定义

### 4.1 清单协议（插件自述）

每插件一份 `插件清单.json`，声明它能解析什么、精度多高、如何被调用。

```json
{
  "协议版本": "v1",
  "语言": "rust",
  "显示名": "Rust 符号解析",
  "文件后缀": [".rs"],
  "入口": ["cargo", "run", "--quiet", "-p", "hm-symext", "--"],
  "能力": {
    "符号": "高",
    "导入": "高",
    "实现": "高",
    "调用": "中"
  },
  "备注": "调用边基于语法级解析，宏展开与动态分发不计入"
}
```

字段约束：

| 字段 | 必填 | 说明 |
|---|---|---|
| `协议版本` | 是 | 与引擎不匹配则拒绝加载，并提示升级 |
| `语言` | 是 | 引擎据此做后缀冲突检测（两种插件抢同一后缀须报错） |
| `文件后缀` | 是 | 引擎分发的唯一依据 |
| `入口` | 是 | 启动插件的完整命令（数组形式，避免引号转义问题） |
| `能力` | 是 | 键为边类型，值为置信度档位；未列出的边视为「不支持」 |
| `备注` | 否 | 记录已知局限，供人排查 |

### 4.2 产出协议（符号与边）

调用约定为批处理，一次进程调用处理一批文件：

```text
<入口> --项目根 <路径> --清单 <文件列表> --输出 <json路径>
```

产出结构：

```json
{
  "协议版本": "v1",
  "语言": "rust",
  "符号": [
    {
      "id": "rust::hm-symext::插件调度::调度",
      "种类": "函数",
      "名": "调度",
      "全名": "hm-symext::插件调度::调度",
      "文件": "鸿蒙/基础能力-域/符号解析-府/插件调度-殿/…/调度.rs",
      "行": 42,
      "可见性": "pub",
      "容器": "rust::hm-symext::插件调度"
    }
  ],
  "边": [
    {
      "从": "rust::hm-symext::插件调度::调度",
      "到": "rust::hm-symext::产出校验::校验",
      "类型": "调用",
      "置信度": "高",
      "位置": { "文件": "…/调度.rs", "行": 88 }
    }
  ],
  "悬空": [
    {
      "从": "rust::hm-symext::插件调度::调度",
      "目标文本": "动态派发目标",
      "类型": "调用",
      "置信度": "低"
    }
  ],
  "诊断": [
    { "级别": "警告", "文件": "…", "信息": "宏展开内的符号未展开" }
  ]
}
```

要点：

1. `符号` 与 `边` 的 `id` 必须在**同一插件内自洽**，且跨两次运行稳定。
2. `悬空` 中 `到` 缺失，改用 `目标文本` 记录原始标识符——诊断层据此比对"代码调用了不存在的东西"。
3. `诊断` 是插件向人报告自身局限的通道，不参与图谱合并。
4. 产出文件自身必须被排除在扫描之外，保证引擎幂等。

### 4.3 统一边词表

各语言的原生概念必须映射到同一套边词表，诊断层才能跨语言写同一套规则。

| 边 | 语义 | 典型产出者 |
|---|---|---|
| `包含` | 文件 / 模块含符号 | 全部插件 |
| `导入` | `use` / `import` / `require` | 多数插件 |
| `定义` | 符号的定义处 | 多数插件 |
| `实现` | trait impl / 接口实现 | 面向对象语言 |
| `调用` | 函数级调用 | 高精度插件 |
| `依赖` | crate / 包级依赖 | 由 `cargo metadata` 等产出 |

禁用自造边类型；确需新增须先改本节。

### 4.4 ID 规范

```text
<语言>::<包名>::<模块路径>::<符号名>
```

| 约束 | 说明 |
|---|---|
| 不含行号 / 列号 | 位置信息放 `位置` 字段，不进 ID |
| 不含绝对路径 | 仓库内相对结构，保证换机器可复现 |
| 分隔符固定 `::` | 避免与语言自身的 `::`（Rust）冲突时，以「最后一段为符号名、其余为容器链」解析 |
| 容器可指向符号 | 嵌套符号（方法在结构体内）通过 `容器` 字段成边，不靠命名拼接 |
| **唯一键是 `(ID, 种类)`**，不是单独的 ID | 语言可能允许同名符号分居不同命名空间（Rust 的类型 / 值命名空间：`struct 任务快照` 与 `fn 任务快照` 可共存）。若把种类塞进 ID，每门语言都要为 ID 变长付代价，且一旦冲突规则变化就会让既有 ID 漂移；故唯一性由 `(ID, 种类)` 承担，ID 本身保持纯净。下游按 ID 建索引时须以 `(ID, 种类)` 为键 |

### 4.5 置信度分级

| 档 | 判定标准 | 举例 |
|---|---|---|
| 高 | 编译级精确 | rust-analyzer、TypeScript compiler、语言官方 AST |
| 中 | 语法级可靠 | `syn`、tree-sitter |
| 低 | 启发式 | 正则、文本匹配 |

诊断层必须据此分级采信：`入度为零且非入口` 仅在**高**置信度下可判"死代码"，中低置信度只能标"疑似"。

## 五、引擎职责与降级

### 5.1 职责链

```text
1. 读「解析定义.json」        → 得知启用哪些插件
2. 读各插件「插件清单.json」   → 校验协议版本与字段完整性
3. 按文件后缀分发             → 每插件一次批处理调用
4. 校验产出 schema            → 不合格产出丢弃并告警，不中断整体
5. 归一化                     → join 坐标索引补坐标；边类型映射到统一词表
6. 合并输出                   → 符号索引.json + 符号索引.md
```

### 5.2 降级矩阵

| 情况 | 行为 |
|---|---|
| 某后缀无插件 | 该文件只保留坐标层信息，不报错 |
| 插件进程崩溃 | 记录该插件失败，其余插件照常 |
| 产出 schema 不合格 | 丢弃该插件产出，告警，其余照常 |
| 协议版本不匹配 | 拒绝加载该插件，提示升级 |
| 两插件抢同一后缀 | 拒绝启动，报冲突（不得静默择一） |

**原则**：任何单点失败都不得使整张图谱失败；宁可某语言符号层为空，不可让整次生成中断。

## 六、九根六层定位

代码与数据分离归位：

| 物 | 性质 | 归位 |
|---|---|---|
| 坐标定义、解析定义、插件清单、索引产出 | 数据 | `.传承/图谱/知识图谱/` |
| 引擎与插件实现 | 代码 | 鸿蒙（见下骨架） |

骨架（**已落地**）：

```text
鸿蒙/基础能力-域/
├── 符号解析-府/                 ← 引擎 crate（hm-symext）：语言无关
│   ├── Cargo.toml
│   ├── 模块.rs
│   ├── 契约定义-殿/             ← 数据契约：清单 / 产出 / 符号 / 边 / 置信度
│   │   └── 契约模型-阁/
│   │       └── 契约-数据-园/
│   ├── 插件调度-殿/             ← 发现 / 校验 / 调度 / 合并
│   │   └── 调度编排-阁/
│   │       └── 编排-逻辑-园/
│   └── 产出校验-殿/             ← schema 与协议版本校验、归一化去重
│       └── 契约校验-阁/
│           └── 校验-逻辑-园/
└── rust解析-府/                 ← 插件 crate（hm-symext-rust）：独立二进制、每语言一府
    ├── Cargo.toml
    ├── 模块.rs
    ├── 主程序.rs                ← 插件入口（`--项目根` / `--清单` / `--输出`）与整层缓存
    └── 符号提取-殿/
        └── 源码扫描-阁/
            ├── rust-模块-园/    ← 语法层：tree-sitter 提取符号与 `包含` 边
            ├── crate-扫描-园/   ← 单元包层：读 Cargo 清单出 crate 符号与 `依赖` 边
            └── 调用-扫描-园/    ← 语义层：rust-analyzer 出 `调用` 边
```

**引擎与插件分属两个 crate**（2026-09-12 拆分）：依赖方向单向——插件 `hm-symext-rust` 依赖引擎 `hm-symext` 取契约类型，反向不成立，故无环。这样 tree-sitter 与 `ra_ap_*` 的庞大依赖图只挂在插件上，引擎侧依赖收敛为 `serde` / `serde_json`，既满足验收基线 1（引擎零语言名词），也使编辑器载入引擎 crate 不再被那份重依赖拖慢。

定位理由：符号解析是诊断、IDE 提示、agent 上下文推送共同依赖的能力，**服务全部九根**，符合 `完整架构蓝图.md` 对鸿蒙"只放跨域共享底层能力"的定义；且它是 Rust 代码，须遵守"代码落园"。

> **命名已裁定（2026-09-12）**：保留 `rust解析-阁`。语言名无通行中文对译，属 `rules/命名规则.md` 第五节所称"强制情况"，可豁免；且不译反而让多语言插件各有同级格子（`js解析-阁` 等）。

### 7.2 步 5 的两处实现要点

- **类型驻留表是 thread-local**：新版解算器要求所有触及类型推断的调用都在 `ra_ap_hir::attach_db(&db, || …)` 作用域内执行，否则 panic `Try to use attached db, but not db is attached`。故整个语义扫描循环被该作用域包住。
- **语义层只做桥接，不新增符号**：`调用-扫描-园` 沿用语法层已产出的 `函数` 符号建「文件 → 行 → 符号 ID」索引，把语义层的定义位置映射回既有 ID。符号判定权始终归语法层，避免两套提取器互相打架。自递归不成边（否则"死代码"的入度会被自己撑住）。

### 7.3 语法层下钻（本次补齐）

`解析文件` 原先只遍历根节点的 `named_children`，`impl` 与内联 `mod` 体内的符号一个都不登记——`包含` 边的另一端悬空，方法调用也无处桥接。现改为递归 `收下`：

| 规则 | 说明 |
|---|---|
| 下钻范围 | 仅 `impl_item` 与 `mod_item`（取 `body` 字段）。**不下钻函数体**：函数体内的嵌套条目属局部作用域，纳入只会给"死代码"判定添噪声 |
| ID 生成 | `<容器 ID>::<名>`，逐层接在容器后面；同时写入 `容器` 字段（§4.4 要求嵌套靠 `容器` 成边）。`全名` = ID 去掉 `rust::<包名>::` 前缀，与旧版顶层项写法一致，未产生额外漂移 |
| `mod x;` 声明 | 没有 `body`，下钻自然止步 |
| `impl` 块命名 | 无 `name` 字段，用被实现类型；**带 trait 时一并带上**（`impl Display for 错误`）。否则同一类型的多个 trait impl 会算出同一个 ID，其方法跟着撞 |

### 7.4 归一化去重（本次补齐）

同一插件内部可能把同一个逻辑节点产两遍，引擎在合并前按唯一键去重（`产出校验-殿/契约校验.rs` 的 `去重产出`）：

| 对象 | 键 | 处理 |
|---|---|---|
| 符号 | `(ID, 种类)` | 重复的丢弃，保留先出现的一条 |
| 边 | `(从, 到, 类型)` | 同上 |

已知来源：`模块.rs` 里的 `mod X;` 声明与 `X.rs` 的文件级模块符号会算出同一个 ID——二者本就是同一个逻辑模块被声明了两遍。不去重会让入度统计把同一节点算两次，直接失真"死代码"判定。

- 保留文件路径排序在先的那条（`收集文件` 已 sort，故可复现）。因此 `...::园::X` 的位置通常落在 `模块.rs` 的 `mod X;` 声明行；`X.rs` 内子项的 `包含` 边仍从该 ID 出发，不受影响。
- 同 ID 异种类的对数会写进插件状态（`插件状态.信息`），可见而不静默。
- 配套修正：`X.rs` 文件级模块符号的 `容器` 由 crate 根改为父模块（`a/b/模块.rs` 的容器是 `a`），与 `mod` 声明侧对齐，否则两边合并时会打架。

### 7.5 已知欠账（不阻塞步 5，但压制其覆盖率）

| 欠账 | 影响 |
|---|---|
| `导入` / `定义` 两类边未实现 | 步 3 的完成判据尚未完全满足 |
| 模块符号行号恒为 1；ID 用文件路径而非 Rust 原生模块路径 | ID 偏长，且与 `mod` 声明路径不对齐；`#[path = "…"] mod X;` 这类写法下，声明出的模块名与目标文件的模块路径不同名，会各留一个节点 |
| 悬空总数仍为 0 | 验收基线 7（悬空可见）尚未构造样例验证 |

### 7.6 性能：拆 crate、载入策略与整层缓存（本次补齐）

全量索引的最大成本在 rust-analyzer 载入工作区，分三层处理：

| 手段 | 做法 | 效果 |
|---|---|---|
| 引擎/插件拆 crate | 重依赖（tree-sitter、`ra_ap_*`）只挂插件 crate | 引擎依赖收敛为 `serde` / `serde_json`；验收基线 1 达标 |
| 载入策略 | `CargoConfig { no_deps: true, sysroot: Some(Discover) }` | `no_deps` 使 cargo 只返回 workspace 成员，不再把整张依赖图的源码装进 VFS；`sysroot` 找回 std 源码，恢复 trait / 方法解析 |
| 整层缓存 | 指纹一致即复用上次产出，跳过本次全部扫描 | 首跑 36.6s → 命中 0.3s |

**载入策略 A/B**（同一仓库、同一插件代码，仅改 `CargoConfig`）：

| 方案 | 配置 | 耗时 | 边总数 | `调用` 边 |
|---|---|---|---|---|
| 极速 | `no_deps: true` | 16.6s | 3216 | 396 |
| **均衡（采用）** | `no_deps: true` + `sysroot` | 52.6s | 3343 | 523 |
| 全量 | `no_deps: false` | 79.2s | 3346 | 526 |

三档符号数完全一致（3050）——`no_deps` 只影响 `调用` 边：关掉依赖后外部 trait 的方法解析不出，`调用` 边掉约 25%。故取均衡档，以载入耗时换回近乎全量的调用边。

**整层缓存**（插件侧 `主程序.rs`）：

- **指纹必须覆盖插件的全部输入**：插件版本 + 协议版本 + 文件清单 + 全部 Cargo 清单 + 全部源文件内容。也必须在**插件侧**——引擎语言无关，不可能知道某门语言的插件还读哪些文件（本插件就额外读 `Cargo.toml` 产出 `依赖` 边）。指纹若落在引擎侧便天然漏项：只改 `Cargo.toml` 时会错误复用旧产出，让陈旧数据入库。
- **粒度是整层**：语义层是 salsa 数据库，既无分块能力也无序列化接口，只能整层命中或整层重扫。
- **位置**：`.传承/记忆/缓存/`（`rust解析-产出.json` + `rust解析-指纹.txt`），该目录由 `.gitignore` 排除（规范 §二/§七：记忆区属运行状态）。
- **写回顺序**：产出先落盘、指纹后写。指纹是「此产出有效」的标记，反序会留下错配，下次把陈旧产出当新的复用。
- **失效边界**：只认内容、不认 mtime，故仅触碰文件时间戳不触发重扫；内容变化（哪怕只加一个空行）或清单增删、插件版本升级则必然失效。

**实测**：首跑（未命中）36.6s（多次实测 37–52s，随机器负载浮动）→ 命中 0.2–0.3s，产出完全一致（坐标索引重建后：符号 3102 / 边 3418 / 悬空 0）。

## 八、验收基线

| # | 基线 | 验证方式 |
|---|---|---|
| 1 | 引擎零语言名词 | 对引擎源码 grep `rust`/`js`/`python` 等语言名，零命中 |
| 2 | 新增语言不改引擎 | 加一份新插件清单后引擎无需改动即可调度 |
| 3 | 幂等 | 连跑两次，产出字节数一致 |
| 4 | 降级不中断 | 删掉插件清单（模拟未接入），引擎正常退出且仅缺符号层 |
| 5 | 单点失败隔离 | 注入一个必崩的假插件，其余插件产出不受影响 |
| 6 | ID 稳定 | 仅改动某文件的空行，重跑后该文件符号 ID 不变 |
| 7 | 悬空可见 | 构造一处调用不存在函数，产出中出现对应悬空记录 |

## 九、风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 置信度被下游忽略 | 中置信度的"死代码"被误当结论清理 | 诊断层强制携带置信度；清理建议须人确认 |
