# 「洪荒·世界」科学研究报告 —— 学术定位、科学性审查与质量度量

> 定位：以科学方法（可证伪、可复现、有对照）对本项目做一次横切体检，回答三个问题——**项目在学术前沿中处于什么位置、设计哲学有多少真正落地、与前沿差多少且方向是否正确**。读者为项目决策者与后续设计者。
> 不解决什么：不修复任何缺陷、不产出新功能设计、不替代 `rules/` 的权威条文；本报告只做**证据盘点与判断**，所有治理动作需另立任务。

**关联**：`传承殿/项目现状清单.md` §五（测试与门禁现状）、`传承殿/设计原则-域/核心设计原则.md` §一~五（六大概念）、`传承殿/设计原则-域/AI_Agent前沿调查.md` §十（前沿关联）、`传承殿/缺陷清单.md`（缺陷盘点档案）。

**方法声明**：本研究采用四线并行的混合方法——① 前沿文献检索（WebSearch，中英文）；② 架构静态审查（读代码核验文档主张）；③ 命令级客观度量（`cargo` 实跑、文件统计）；④ 实证证据审计 + 一次真实端到端基准尝试。凡无法验证者一律标注「待核实」，凡未找到者明确写「代码中不存在」。

## 一、研究时间锚与关键方法学警告

### 一·一、代码快照与"移动靶"问题

| 项 | 值 |
|----|----|
| 研究日期 | 2026-09-12 |
| git HEAD | `10ffe3a`（chore(治理): .gitignore 忽略 .传承/记忆 运行状态） |
| 工作区状态 | **脏（M Cargo.toml、?? 代码文档-府/）** |
| 后端运行态 | 运行中，`/api/dev/pilot/status` → `就绪=true` |

**警告（最重要的方法学事实）**：研究期间，工作区被**并发修改**。证据链如下：

1. 本研究首次读取 [Cargo.toml](file:///f:/洪荒 - 世界/Cargo.toml) 时，`members` 为 **39** 条，**不含** `鸿蒙/基础能力-域/代码文档-府`；
2. 数分钟后以命令行复核，`members` 变为 **40** 条，**第 17 条即** `鸿蒙/基础能力-域/代码文档-府`；
3. `git status` 显示 `Cargo.toml` 为 ` M`（已改未提交），`代码文档-府/` 为 `??`（未跟踪新目录）；
4. 该府 [Cargo.toml](file:///f:/洪荒 - 世界/鸿蒙/基础能力-域/代码文档-府/Cargo.toml) 当前为 **0 字节空文件**。

**推论**：该时刻磁盘状态**无法构建**（`cargo` 报 `manifest is missing either a [package] or a [workspace]`）。运行中的后端是**旧版本产物**。

> **后续核实（2026-09-12 同日，v1.2 补注）**：该府 `Cargo.toml` 随后被补全（954 字节，声明 `hm-docgen`），复核 **members=40、清单异常=0**，**可构建性已恢复**。故上文"工作区被并发修改"为**瞬时状态**，读者不应据此认为项目长期不可构建。此补注本身即为本章方法学警告的例证：**本报告的数字同样带时间戳**。

**根因（2026-09-12 经所有者确认）**：该现象**并非项目缺陷**，而是**同时有 3 个智能体并行操作同一工作区**所致——一方的读取会撞上另一方的"半成品写入"（典型如 `Cargo.toml` 已登记新成员、而该成员的清单文件尚为空）。

由此得出一条**可推广的工程风险**：

> **多智能体并发写同一工作区，会破坏可构建性与可复现性。**

这与本项目自身的"多智能体协作"议题恰成互文：项目在**运行时**设计了看板锁、角色校验、跨层熔断来约束并发；但在**开发时**（AI 改代码这一层）尚无同等约束。缓解方式见第八章建议 11。

> 这一事实对本报告的意义：**任何"项目当前状态"的结论都自带时间戳，且分钟内即可能失效**。学术意义上的可复现性，在此项目上首先被"工作区被并发写入"这一工程现实所削弱。

### 一·二、未能完成的实验与其价值

原计划实跑一次真实端到端基准以补齐"复跑三指标缺原始 stdout"的证据缺口。**实跑失败**，失败链完整记录如下（见第六章），其本身即为一手实证发现。

**小结**：本章确立两条基线——代码快照以 git HEAD 为准，工作区被并发修改导致"当前状态"具有分钟级有效期；实证实验因环境阻塞未能完成，转为证据审计。

### 三·二、真创新 vs 重造轮子

**可能站得住的四点是**：

1. **相克的"只加约束、不删数据"语义**——与主流"上下文压缩即丢弃"（Anthropic compaction、ACON）方向相反，检索范围内未见对应物。
2. **三态认知的"双排序检索决策链"**——把"先问哪一层"（使用优先级）与"更信哪一层"（置信度）显式解耦为两套正交排序。
3. **规则单源的双层分流治理**——人工权威条文与引擎提炼的运行时事实规则强制不可混存。
4. **跨层共享退化检测器 + 跨层回退熔断**——单检测器贯穿多角色，多数开源 Agent 只做单层循环上限。

> **重要限定**：以上"独创性"判断的依据是"**检索范围内未发现对应物 + 项目自述**"，**不等同于学术首创**。若需对外主张，必须先做正式 prior-art 检索。

**明确属于重造轮子的是**：六层多角色流水线、澄清对话状态机、看板任务流转、LLM 多供应商故障转移、本地语义检索、契约单一真相源。

### 四·二、五行相生在生产路径不闭合（关键缺陷）

审查发现三条相互叠加的事实：

1. **后段链路缺触发器**：`金生水` 需 `RuleSet::评估` 被调用，而非测试调用点全仓只有一处——`演示模块.rs` 的 `演示闭环`，由 `run_self_test` 开关控制，启动模块明确"**默认关闭，避免污染真实业务数据**"。生产热路径无人调用 `评估`。
2. **环不闭合**：即便触发，`水生木` 创建的是 `TaskStore` 中 `待受理` 的任务，而 `TaskStore` 无任何自动化把 `待受理` 推进到 `已完成`；只有自检演示手工 `推进(任务, 已完成)` 才让环闭合。
3. **双轨对象（最根本）**：**五行环挂在 `TaskStore`，真实开发流水线挂在 `TaskBoard`**，二者是不同对象、不同状态枚举，仅共享信号总线。`TaskBoard` 发出的 `任务完成` 只驱动前半段，其下游写入 `TaskStore`，**不会回流到 `TaskBoard`**。

**结论**：相生链在 `zd-linkage-test` 层面可逐段验证为真（16 个测试），但"**生产环境自持闭环**"不成立——它是一个由演示/测试驱动的、与真实看板流水线**平行的缩影模型**。

### 四·三、不可证伪的隐喻清单

以下主张**无法用实验检验**，因为它们不给出任何可观测变量或阈值：

1. **六道轮回 / 业力 / 技术债务**——无状态枚举、无债务度量、无升降级阈值。项目自己的《量劫迭代引擎》文档亦自认"技术债务模型、焚炼阈值（后续，需债务度量）"。
2. **九五至尊的"居中不偏 / 高而不悬 / 位正则吉"**——"居中"无可度量，"唯一决策点"无代码实体。
3. **四角色的"不可兼任"**——身份层无实现，无法设计任何"同一主体不得自验"的实验。
4. **五行归位的因果主张**（"相生相克规律应决定依赖关系、避免循环依赖"）——实际 `hm-linkage` 的依赖图与五行生克无对应；它只是把所有引擎聚到一点。

### 四·四、真正的科学性风险

风险不在于"用了隐喻"，而在于**验收体系把隐喻当作已交付**。已发现的实例：

| 验收主张 | 实际 |
|---|---|
| "各引擎与装配府内部 **0 测试**" | 生产代码中 **8 个文件**含 `#[cfg(test)]` |
| "全部 **20 个 crate**"（验收报告） | 现为 **40** 个 members |
| "共 **38 个测试**"（验收报告） | 现为 **528** |
| 六道被描述为"质量流转机制" | 代码零实现 |

即：**"文档即完成"的自证式叙述，替代了可复现的量化证据**。

**小结**：项目把一套"发布订阅级联 + 容量护栏 + 状态机治理"的真实工程，包装在五行/六道/九五的话语中。**三态认知、角色状态机、熔断回退是可量化机制；六道、业力、九五至尊是不可证伪隐喻**。后续审查应一律以 `cargo` 实跑输出与可复现阈值断言为准，而非以验收报告勾选表为准。

## 六、实证实验：实跑记录与证据审计

### 六·一、本次实跑（一手记录）

按计划对 `.传承/门禁/端到端基准.ps1`（任务=斐波那契模块）发起真实运行。**失败**，原始输出如下：

```text
========== 端到端基准 · 真实 LLM 全链 ==========
后端地址：http://localhost:8321
驱动台就绪：是

[任务 1/1] 发布：写一个返回斐波那契数列第 n 项的模块，附带单元
Invoke-WebRequest: 端到端基准.ps1:42:15
   | IO 错误: 磁盘空间不足。 (os error 112)
```

处置过程与结果：

| 步骤 | 动作 | 结果 |
|---|---|---|
| 1 | 检查后端 | `就绪=true, 运行中=false`（可跑） |
| 2 | 定位空间 | F 盘 **0.00 GB** 空闲；`target/` = 15.49 GB |
| 3 | `cargo clean` | **失败**：`代码文档-府/Cargo.toml` 缺 `[package]` → **工作区已不可构建** |
| 4 | 手动清理 `target/` | 仅释放 ~1.07 GB，余 14.4 GB 被**运行中进程锁定** |
| 5 | 结论 | **实验阻塞终止** |

**因果链（关键判断）**：要释放 `target/debug` 的锁，必须停掉后端；而后端一旦停止，**因工作区已损坏而无法重新编译启动**。故实验不可完成——这是**环境/工程状态的双重阻塞**，而非脚本缺陷。

**该失败本身的三条实证价值**：

1. 端到端基准**不具备单机可复现性**：依赖 ≥15 GB 空闲磁盘 + 可编译的工作区 + 可释放的运行进程，三者任一不满足即整体失败。
2. 工作区处于**已损坏且被并发修改**的状态（详见一·一），"528 测试全绿"的宣称在当前磁盘快照上**无法被独立复核**。
3. 项目宣称的"零配置直接跑"在实际机器上被磁盘与并发写入两个现实变量击穿。

### 六·二、已有实证证据强度审计

| 证据 | 指标值 | 样本量 | 对照 | 强度 |
|---|---|---|---|---|
| 端到端首跑（2026-09-09） | 100% / 100% / 50% | n=2 | 无 | 弱-中 |
| 端到端复跑（2026-09-11） | 100% / 100% / 50% | **n=1** | vs 首跑"一致" | **弱** |

### 六·三、被过度归纳的结论

1. **"无人干预率 100%"** —— n=1 时 95% 置信区间约 **[21%, 100%]**，n=2 时约 **[34%, 100%]**，点估计无统计意义。更严重的是**概念偷换**：系统**不存在人工干预入口**，该指标实为"**自主走完全链率**"。
2. **"测试通过率 100%"** —— 分母是"有测试动作的会话"而非全部任务，**未跑测试的任务不进分母**，构成幸存者偏差。
3. **"复跑与首跑一致"** —— n=1 vs n=2，无法区分"一致"与"巧合"；且**修复后三指标的原始 stdout 未在磁盘留档**，文档三处（现状清单/缺陷清单/修订记录）互引而无独立日志。**这是复现性硬伤**。
4. **"熔断显著有效"** —— 对照实验每组 n=1，且修复同时改变了**三个变量**（作用域跨实例、签名归一、阈值 3/5→2/3），**无法归因**。
5. **测试总数口径混乱** —— 502 / 489 / 492 / 510 / 526 / 528 并存，引用任一数字都须注明时点。

### 六·四、可复现实验方案（设计，未执行）

通用约定：固定模型与版本（现为 `MiniMax-M3`）、固定 `timeout=300s`、每次清空 `道果/持久化` 与 `工作区/`、每组前校验 8321 端口空闲、**保存原始 stdout 而非仅文档转述**。

| 实验 | 假设 | 自变量 | 因变量 | 样本量建议 | 判定标准 | LLM 调用估算 |
|---|---|---|---|---|---|---|
| 1 熔断有效性 | 开启熔断降低空转轮数与耗时 | 熔断开/关（或修复前/后版本） | 空转轮数、终止耗时、是否触发、终态 | 配对 n≥10 / 组间每组 n≥20 | Wilcoxon 符号秩 / Mann-Whitney U；触发率用 Fisher | ~400 |
| 2 六层协作 vs 单循环 | 协作成功率更高 | 驱动模式 | 成功率、三指标、耗时、调用数 | 每模式 ≥90（任务分层 × R=3） | Fisher / 逻辑回归（含难度协变量） | 1,800-5,400 |
| 3 认知注入 开/关 | 注入降低返工率 | 认知装配开/关 | 返工率、首过率、token 量 | 每组 ≥58（检测 50%→25%，α=.05, power=.8） | 两比例检验 + 效应量 | 1,200-3,600 |
| 4 多任务端到端成功率（主实验） | 估计真实成功率区间 | 任务难度分层 | 三指标、耗时、调用数 | 每层 ≥30，总 ≥90-270 | Wilson 区间；分层报告防 Simpson 悖论 | 2,700-8,100 |

**样本量依据**：以 0 失败声称成功率 ≥90% 需 n≥29、≥95% 需 n≥60、≥99% 需 n≥300（Rule of Three）。**合计约 6,000-17,500 次 LLM 调用、数十小时机时。**

**一次性基建投入**：① 脚本增加结构化 JSON 结果落盘（任务 id / 终态 / 轮数 / 耗时 / 模型 / 时间戳）；② 记录模型、温度、timeout 与工作区快照哈希；③ 对"返工"建立 30 条人工金标准以校验正则口径的灵敏度/特异度。

**小结**：实证基础目前为**冒烟级**——单任务、单轮、无随机性控制、无对照、n≤2。最可信证据是 `cargo test` 全绿（含熔断回归）；最需要补的是**修复后三指标的原始 stdout**与**熔断实验的变量隔离**。

## 七、差距量化与方向判断

### 七·一、差距总表

| 层面 | 本项目 | 前沿 | 差距 |
|---|---|---|---|
| 可靠性机制（熔断/限流/回退） | 跨层熔断、限流不删数据、四步安全删除 | 单层循环上限为主 | **持平 / 局部领先** |
| 契约与规则治理 | 单一真相源、规则双层分流 | policy-as-code、DbC | **轻量层持平 / 形式化层落后 3 年+** |
| 记忆与检索 | 字符哈希嵌入 + 阈值检索 | 神经 embedding + 向量库 + 图记忆 | 落后 1-2 年 |
| 多智能体协作 | 五角色固定流水线 | 动态编排 + 实测收益数据 | 落后约 1 年且缺验证 |
| 自主编码能力证据 | 自建三指标（n≤2） | SWE-bench Verified 96-97% | **不可比** |
| 评估方法论 | 无标准基准、无 pass^k | SWE-bench / τ-bench / AgentBench | **落后 2-3 年（最关键）** |
| 生态与互操作 | 自研全栈、无 MCP | MCP 事实标准、SDK 生态 | 落后 3 年以上 |

### 七·二、方向准确性判断

**判断正确的部分**：

1. **"契约即约束 / 规则单源"方向正确**——2024-2026 前沿整体在朝"把不可检验的自然语言意图转为可检验规约"演进（PACT / SpecPylot / vericoding / Lean-Agent Protocol），项目方向一致，只是停在最轻量的一档。
2. **"可靠性优先于能力"取向正确**——循环与退化是生产级 Agent 的头号故障，项目提前内置熔断与跨层回退。
3. **"纯后端 + 契约化对外接口"无错**——零耦合利于被集成，不与主流冲突。
4. **"限流不删数据"在记忆一致性上合理**——代价是存储与检索压力上升。

**判断偏了的（三条）**：

1. **"自研全栈中文架构"在工程效率上偏**。前沿收敛方向是**复用标准生态**（MCP、LangGraph、向量库、SWE-agent 脚手架）；项目自建信号总线、契约、容器、嵌入器、看板、接待机全套，**重复实现成本高且无法接入既有生态**，收益与投入不成比例。**但此条需按七·四的约束重估**——它并非单纯的选型失误，而是有代价的自洽选择。
2. **"所有任务都走固定多角色流水线"存在被前沿否证的风险**。Anthropic 明确建议"默认单 Agent，仅在上下文隔离/并行/工具过载三类场景才上多 Agent"，实测多 Agent 耗 token 为单 Agent 的 **3-10×**；Cognition 主张"一个大脑一条思维流"。项目**缺少"是否值得多智能体"的触发判断**。
3. **"契约"一词的语义层级偏轻**。对外宣称"契约即约束"易被理解为 DbC/形式化契约，实际是接口契约 + 单一真相源，**名实层级需澄清**。

**明显缺失的关键能力**：

| 能力 | 状态 | 优先级 |
|---|---|---|
| SWE-bench 类标准化评测 | **完全缺失** | 最高 |
| 真实仓库级任务验证（非"开发自身"） | **完全缺失** | 最高 |
| pass^k 类一致性/稳定性度量 | **缺失** | 高 |
| 真向量检索（神经 embedding + ANN） | 半缺（仅字符哈希） | 中 |
| OS 级沙箱隔离（容器/TEE） | 弱（仅工作区+白名单） | 中 |
| 形式化验证（前后置条件/SMT/定理证明） | **缺失** | 中 |
| MCP 等标准化互操作 | **缺失** | 中 |
| 多模态 | **缺失** | 低 |

### 七·三、方向结论

> **方向在"可靠性 + 契约治理"这条主线上是准确的，且局部有真实独创（限流不删数据、双排序检索决策、规则双层分流、跨层熔断）；但路线在"全栈自研"与"默认多智能体"两处偏航，在"评测方法论"上存在致命缺口——项目无法证明自己在任何外部尺度上处于什么水位。**

修正方向的最小动作是：**把资源从"再造一个组件"转向"接入一个外部基准"**。

### 七·四、约束重估：所有者"非程序员 + 仅中文"条件下的路线再判

**新增事实（由项目所有者于 2026-09-12 补充）**：本项目所有者**不具备编程与英文能力**，不读代码、不读英文资料；全部实现由 AI 完成，所有者对项目的理解与验收**只能通过中文**。故"自研全栈"并非偏好，而是**可读性主权**的代价——若直接采用英文生态（MCP / LangGraph / 向量库 / SWE-agent 脚手架），所有者将**丧失独立的审计能力**。

据此对前文判断作三点修正：

1. **"自研全栈"的性质变了**：它是"可读性主权换工程效率"的自觉取舍，**不应简单判为错误**；前文以"前沿都在复用生态"为由的批评，忽略了所有者的审计约束。
2. **批评换了形式但未消失**：自建信号总线 / 嵌入器 / 看板 / 接待机带来**巨大的维护面**——而维护面越大，AI 出错且无人发现的概率越高。**正解既不是"全部重写"，也不是"全盘换英文生态"，而是让 AI 承担英文生态的读写与封装，向所有者只暴露中文契约**。这恰是本项目已在走的方向；问题在于**从未验证过它真的更划算**。
3. **真正的风险被显著放大**：当所有者无法独立阅读代码，**一切信任都压在"AI 的自述"上**。而本报告第四章已证明："AI 写的文档"与"磁盘上的代码"存在**系统性不一致**（members 记 37 实为 40、"府内 0 测试"实为 8 个文件、"六道已实现"实为零实现、"熔断 3/5 次"实为 2/3 次）。

> **由此得出本报告最重要的一条结论**：
> **在此约束下，项目最缺的不是"更完整的中文文档"，而是"不需要所有者阅读也能判真伪的证据"。**
> 文档是给所有者**看**的，门禁是替所有者**验**的。前者可被 AI 写得很漂亮，后者只能被机器判真假。

**对前文评级的处理**：三·三与七·一中的"落后"评级**全部保留**，但**归因改写**——落后主要源于**验证基建缺失**（无标准基准、无机器可验门禁闭环），而非"选错了技术栈"。同理，八章建议的优先级以"**是否阻断证据可信性**"为首要判据，与此约束完全一致。

### 七·五、修正：项目已存在一条机器可验证的文档管线（v1.2 补注）

所有者说明：手写文档久未更新故已失真，因此近期自行推动了「代码文档」能力。经实测核查，该能力**已在运行且经独立抽查为准确**：

| 要素 | 事实 | 证据 |
|---|---|---|
| 事实源唯一 | 文档生成只消费上游符号索引，本府**不解析源码**；`Cargo.toml` 以注释声明硬约束"一旦本府自己解析源码，就会出现第二份真相" | `鸿蒙/基础能力-域/代码文档-府/Cargo.toml` |
| 规模 | 生成 **533 篇**，覆盖 **3,186 个符号**、**3,521 条边** | `.传承/图谱/知识图谱/代码文档/index.md` |
| 事实校验 | **533 篇全通过、0 篇疑似幻觉**，并含"拦截虚构引用"自检 | 同目录 `校验报告.md` |
| **本次独立抽查** | 抽取 `看板数据.md` 逐条比对源码：`TaskBoard` 结构体（L19）、`新建`（L29）、`设置信号总线`（L39）、`发布信号`（L44）、`发布任务`（L51）**行号与可见性完全一致**；调用边 `发布任务→未初始化`(L59)、`生成`(L60)、`保存`(L74)、`发布信号`(L75) **与源码逐行吻合** | `篇/太初__…__看板数据.md` vs [看板数据.rs](file:///f:/洪荒 - 世界/太初/任务管理-域/任务核心-府/任务看板-殿/看板管理-阁/任务看板-数据-园/看板数据.rs) |

**结论修正**：第七章与第五章中"验证基建缺失/门禁退化"的严重度**应部分下调**——项目**已具备**一条"符号索引 → 生成 → 事实校验"的机器可验证管线，且经独立抽查**准确**。这是对标"可读性主权"约束的**正确且已见效**的投入。

**但有三条边界必须认清**（这正是它**不能**替代标准化评测的原因）：

1. **它校验的是"名字有没有出处"，不是"说法对不对"**。`校验报告.md` 自述："校验只针对**事实性**：叙述中出现的符号引用能否在事实图上溯源。**文风与结论质量不在校验范围**。"故"0 疑似幻觉"是**窄口径**结论。
2. **当前叙述器为"模板"**（报告记"叙述器：模板叙述器"），输出以结构化表格为主，尚未启用 LLM 叙述层。
3. **只覆盖"代码里有什么"，不覆盖"状态类数字"**。它无法阻止 `项目现状清单` 把 40 写成 37、把 528 写成 502——**手写状态文档仍会过期**。

**引申建议**：把一切"会变的数字"（members 数、测试数、门禁结果、各域计数）改为**由该管线生成或校验**，人手只写意图与判断。如此"文档是错的"这类问题才被根除。
