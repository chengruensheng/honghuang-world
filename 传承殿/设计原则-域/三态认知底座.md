# 三态认知底座设计文档

> **定位**：本文件是「三态认知底座」的完整设计草案，供 AI 深度模拟与推演，找出最优结构后再落地编码。
>
> **要解决的问题**：让 AI 彻底明白一个项目，从而能准确修复、开发。
>
> **状态**：v0.1 · 2026-09-05（设计草案，待深度模拟优化）

---

## 一、背景与要解决的问题

### 1.1 项目自身定位

「洪荒·世界」是一个用 Rust workspace 构建的、能**自主开发自身**的智能体系统。它已经有五行引擎（任务/迭代/记忆/规则/事件闭环）和自主开发智能体（LLM 决策 + 工具调用 + 本地执行器）。

现在的瓶颈是：**智能体「读不懂」一个项目，导致改错、乱改、漏改。** 需要一套「认知底座」，让智能体在动手前，对项目形成完整、准确、可追溯的理解。

### 1.2 AI 开发的典型缺陷（业界实证）

SWE-bench（评估 AI 修复真实 GitHub issue 的基准）揭示的 AI 开发失败模式：

| 缺陷 | 根因 | 说明 |
|------|------|------|
| 定位错误 | 找不到正确的修改位置 | 改错文件、改错函数 |
| 理解不足 | 不懂代码意图就动手 | 把正确逻辑改成错的 |
| 约束违反 | 违反项目规范/门禁 | 踩了项目明令禁止的红线 |
| 验证不足 | 改完不测试就交付 | 交付了跑不通的代码 |
| 环境问题 | 依赖/环境装不上 | 构建失败、版本冲突 |
| 范围蔓延 | 越改越多、改错范围 | 一次改动波及无关模块 |
| 重蹈覆辙 | 踩同样的坑 | 不记得历史教训 |

**这些缺陷的共同根因**：AI 缺乏对项目的「世界」「规则」「目标」「历史」的完整认知，只靠临时的代码片段拼凑理解。

## 二、三态认知底座总览

### 2.1 一句话本质

**用三种不同本体、不同可信度、不同成本的认知来源，组成一条「先快后准」的检索链，让 AI 既省成本又不出错地理解项目。**

### 2.2 三态一览

| 态 | 别名 | 本体（是什么） | 注入方式 | 持久化 |
|----|------|---------------|---------|--------|
| 图谱 | 世界态 | 代码真源，客观实在 | 拉（按需，少量多次） | 落盘，实时更新 |
| 格位 | 心智态 | 提炼摘要，主观认知 | 推（每格最新摘要全量常驻） | 落盘，更新即写 |
| 临时 | 过程态 / 上下文 | 执行记录，运行轨迹 | 流（有就加，超阈值压缩） | 落盘，可恢复 |

> 术语说明：第三态早期称「过程上下文」，后与用户对齐，明确其「临时性、流式、可压缩」本质，简称「临时」。本文档统一用「临时」指代第三态，与「过程上下文」「执行语境」同义。

### 2.3 三态为何互补

- **图谱**回答「代码到底是什么样」——客观、不可辩驳，但检索成本高。
- **格位**回答「我该怎么理解它」——快、常驻，但是主观提炼，可错。
- **临时**回答「刚才实际发生了什么」——真实过程记录，但会膨胀、需压缩。

三者不是三个并列的存储池，而是「摘要（格位）→ 记录（临时）→ 证据（图谱）」的**层次关系**（详见第六节）。

## 三、三态各自定义

### 3.1 图谱（世界态）

- **本体**：客观实在，代码即真源。毫秒级实时反映代码真实状态。
- **内容**：模块、符号（函数/类型/常量）、依赖边、导出、引用。
- **语言无关**：核心图模型只用通用概念（模块/符号/依赖边/导出/引用），语言差异收敛到适配器（Rust 适配器读 Cargo.toml + pub use；tree-sitter 可复用 158 种语言）。
- **检索方法**：查依赖、被谁依赖、查符号等。
- **注入方式**：拉——需要细节时才少量多次加载，只给最相关的一段。

### 3.2 格位（心智态）

- **本体**：主观认知。AI 对项目各关键面的**提炼摘要**，可错可纠。
- **内容**：36 个格位（6 维度 × 6 格位），见第四节。
- **铁律**：格位只存**有界、可信、适合常驻注入的摘要**；证据与过程记录存格位之外（图谱/临时），防止 AI 用错误总结反向污染。
- **注入方式**：推——每格最新一整段全量常驻，是冷启动捷径。

### 3.3 临时（过程态 / 上下文）

- **本体**：执行过程。AI 实际执行留下的轨迹。
- **内容**：消息角色（系统/用户/助手/工具结果）、语境消息、每轮的工具调用与结果。
- **注入方式**：流——有就加，超过阈值压缩。
- **价值**：还原「做过什么、踩过什么坑」，避免重蹈覆辙。

## 四、36 格位（6 × 6 结构）

### 4.1 6 维度（主轴）

36 = 6 维度 × 6 格位/维度。6 维度是 AI 认知项目的六个方面：

| 维度 | 能力声明 | 内/外 |
|------|----------|-------|
| 内部 | 我是谁、我要做什么 | 内（AI 自己） |
| 外在 | 项目世界的结构/依赖/接口 | 外（整个项目） |
| 规则 | 外部约束/门禁/禁止 | 外（约束） |
| 执行 | 我怎么做（命令/技术栈） | 内（AI 行动） |
| 目标 | 我的方向（当前/未来） | 内（AI 方向） |
| 经历 | 我的历史（事件/教训） | 内（AI 历史） |

**三对正交**：内↔外、规则↔执行、目标↔经历。

### 4.2 每维度 6 格位（完整清单）

| 维度 | 6 个格位 |
|------|----------|
| 内部·我 | 角色 · 能力 · 职责 · 状态 · 记忆 · 边界 |
| 外在·项目 | 定位 · 结构 · 依赖 · 接口 · 环境 · 数据 |
| 规则·约束 | 禁止 · 门禁 · 规范 · 流程 · 例外 · 红线 |
| 执行·行动 | 命令 · 技术栈 · 步骤 · 工具 · 验证 · 产出 |
| 目标·方向 | 当前 · 未来 · 里程碑 · 验收 · 优先级 · 风险 |
| 经历·历史 | 事件 · 教训 · 决策 · 来源 · 时间 · 归档 |

### 4.3 维度特殊性（重要）

- **目标维度**：只有「目标」才需要**初心（为何定）/ 现况（进度到哪）/ 愿景（达成后如何）/ 偏移（偏离校准）**。这「三时间态 + 偏移检测」**不是所有格位的通用字段**，只属于目标维度。
- **执行维度**：其中「命令 / 技术栈 / 工具 / 验证」偏**稳定规范**（适合常驻格位）；「步骤 / 产出」偏**动态过程**（可能更适合交给临时上下文记录）——此为待模拟点，见第八节。

### 4.4 格位数据结构（草案）

```text
格位 {
  维度:       内部 | 外在 | 规则 | 执行 | 目标 | 经历   ← 归属维度
  格位名:     String                                  ← 该维度下第几个切片
  摘要:       String                                  ← 有界可信摘要（常驻注入用）
  可信度:     0.0 ~ 1.0                               ← 判定「够不够用」的依据
  证据引用:   Vec<图谱标识>                            ← 指向图谱中的模块/符号/依赖边
  最后校验时间: 时间戳
}

目标内容（仅「目标」维度格位持有，可选）{
  初心: 最初意图
  现况: 当前进度
  愿景: 达成后形态
  偏移: 现况偏离「初心→愿景」路径的告警
}
```

## 五、核心机制：置信度 vs 使用优先级

这是三态协作的**关键**——两条排序，一条检索链。

### 5.1 两条排序

| 态 | 置信度（信谁） | 使用优先级（先看谁） |
|----|--------------|-------------------|
| 图谱 | **最高**（代码真源，不可辩驳） | **最低**（最后才看） |
| 临时 | 中（真实发生过的记录） | 中 |
| 格位 | **最低**（主观提炼，可错） | **最高**（最先看） |

### 5.2 检索决策链（核心）

```
有疑问 → 先看格位（常驻，零成本）
   ├─ 格位「够」（信息足 + 可信度达标）→ 直接用，不再往下查
   ├─ 格位「不够」→ 看临时上下文（流式记录）
   │     ├─ 上下文够 → 用上下文
   │     └─ 上下文不够 → 查图谱（代码真源）
   └─ 格位可信度低 → 主动查图谱 → 校准/修正格位（纠错闭环）
```

### 5.3 一句话总结

**优先级决定「先问谁」（省成本），置信度决定「信谁」（保准确）。**

- 格位最快但最不可信 → 所以「够」才用，不够就逐级下沉到图谱这个最可信真源。
- 格位与图谱冲突时 → **信图谱**，并回写校准格位（格位被纠错）。

## 六、三态关系（摘要 vs 证据 vs 记录）

三态不是并列的，而是「摘要 → 记录 → 证据」的层次：

```
36 格位（6×6）= 心智地图，只存"提炼摘要"（推，置信度最低，优先级最高）
   ├─ 外在维度格位 → 详情存「图谱」（拉，代码真源，置信度最高）
   ├─ 执行/经历维度格位 → 详情存「临时」（流，运行记录，置信度中）
   └─ 内部/规则/目标维度格位 → 自身即完整（推，常驻）
```

**铁律**：格位只存有界可信的摘要；证据（图谱）与过程记录（临时）存格位之外。防止 AI 用错误总结反向污染格位。

## 七、构建主线与语言无关

### 7.1 构建主线

先构造项目整体模型（图谱）→ 通过模型构建心智（36 格位）→ 根据执行过程获取运行时上下文（临时）。

### 7.2 语言无关底座

核心图模型只用通用概念（模块/符号/依赖边/导出/引用），语言差异收敛到适配器。这样同一套认知底座能理解任何语言的项目。

## 九、待深度模拟/打磨的点（交给其他 AI）

以下问题请模拟推演后给出最优解：

1. **目标维度 6 格位补全**：已知「初心/现况/愿景/偏移」4 个，缺 2 个，应是什么？
2. **36 格位清单验证**：现有 6×6 清单是否覆盖 AI 开发的所有缺陷？有无冗余格位？

4. **检索决策链阈值**：格位「够不够用」的判定标准（可信度阈值如何定？信息不足如何判定？）。
5. **格位 schema 最优形态**：统一骨架 + 目标专属内容（Option）是否最优？还是按维度各自定义结构？

## 十、组织与命名约束（供模拟时遵循）

- 层命名：域=`4字-域`、府=`4字-府`、殿=`2字-2字-殿`、阁=`2字-2字-阁`、园=`名字-类型-园`。
- 非强制情况下严禁 `src` 等英文文件命名；代码落园，无 `src` 目录。
- 数量上限：域 ≤ 3；殿 ≤ 6 阁；阁 ≤ 4 园。
- 单文件 ≤ 350 行（建议）/ ≤ 500 行（硬上限）；单函数 ≤ 50 行。
- 依赖单向无环；证道只测府级公共 API。
- 生产错误走 `Result` + `?`；锁用 `.expect("具体锁名 锁中毒")`。
- 生活比喻（书/老师傅/山川地脉等）严禁进生产代码或注释；生产代码与注释只用工程化、语义化中文名（图谱/心智/过程上下文）。
