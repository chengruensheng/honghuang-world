# 洪荒·世界 完整架构蓝图

> **设计目的**：以 F 盘为基地，从零设计一个新项目。吸收 E 盘的工程教训（结构骨架成熟、但世界观未成为引擎），吸收过往对话的洞察（五行相生可驱动演化、六道轮回可驱动循环），重新推导五行映射，设计一套**世界观与工程一体两面**的架构。
>
> **核心命题**：洪荒世界观不是命名的装饰，而是系统演化的真实引擎。
>
> **状态**：架构蓝图 v0.2 · 2026-09-04（已敲定：临时/非临时处置、层命名规则、数量上限硬约束）

---

## 一、设计总纲

### 1.1 一句话本质

**一个用五行相生驱动演化、六道轮回驱动循环、九根六层保证容灾的意图驱动自主构建系统。**

### 1.2 E盘的教训（为什么要重来）

| E盘的问题 | 根因 | F盘的对策 |
|-----------|------|-----------|
| 五行缺失 | 世界观只停在命名，未兑现为引擎 | 五行相生成为演化引擎 |
| 六层是静态层级 | 只有空间递进，没有循环反馈 | 六道轮回让结构螺旋上升 |
| 九根依赖是单向线性链 | 太初→道韵→量劫→混沌，缺闭合 | 五行相生是闭合循环 |
| 世界观与工程两张皮 | 原语与工程词语分离 | 世界观概念直接承载工程语义 |
| 静态治理机器 | 只防御，不演化 | 自驱演化的活体 |

### 1.3 保留 E盘 的骨架（用户认可的部分）

E盘 的六层结构（维度→域→府→殿→阁→园）本身是**好结构**，其真实工程动机是**容灾性**——这必须保留。F盘 沿用这一骨架，但补齐世界观引擎。

## 二、五行演化引擎（重新推导的映射）

### 2.1 五行 ↔ 五根 的三层对应

五行不再是游离的属性标签，而是**属性 → 维度 → 工程能力**的三层贯通：

| 五行 | 属性（是什么力） | 维度（落在哪根） | 工程能力（兑现为哪个引擎） |
|------|----------------|----------------|--------------------------|
| **木** | 生长、生发、萌芽 | **太初**（存在层） | 任务引擎——存在从无到有 |
| **火** | 转化、焚炼、重生 | **量劫**（时间层） | 迭代引擎——时间中的变革 |
| **土** | 承载、稳定、中心 | **乾坤**（空间层） | 记忆引擎——空间中的承载 |
| **金** | 收敛、规范、成形 | **道韵**（法则层） | 规则引擎——法则的收敛 |
| **水** | 流动、无定形、渗透 | **混沌**（可能层） | 事件引擎——可能性的流动 |

**推导依据**：五行属性与五根本体论含义逐一精确匹配——
- 太初是"存在的萌芽"→ 木（生长萌芽），非对话中的"火"
- 量劫是"毁灭与重生"→ 火（焚炼重生），非对话中的"土"
- 乾坤是"承载万物"→ 土（承载稳定），非对话中的"金"
- 道韵是"法则规范"→ 金（收敛规范），非对话中的"木"
- 混沌是"可能性、无序"→ 水（流动无定形），与对话一致

### 2.2 五行相生 = 闭合的演化循环

```
太初(木) → 量劫(火) → 乾坤(土) → 道韵(金) → 混沌(水) → 太初(木)
 存在       时间       空间       法则       可能       存在
```

| 相生 | 工程语义 | 自洽性验证 |
|------|---------|-----------|
| 木生火 | 存在生长 → 技术债务积累 → 触发变革 | 功能长到一定程度必然引发重构 |
| 火生土 | 变革重建 → 新架构定型为空间结构 | 重构后沉淀为新架构 |
| 土生金 | 结构定型 → 经验收敛为法则 | 架构稳定后总结成规则 |
| 金生水 | 法则明确边界 → 打开新可能性 | 规则划清边界反而释放空间 |
| 水生木 | 可能性流动 → 催生新存在 | 新需求催生新功能 |

**关键**：这个循环是**闭合**的（对比 E盘 的单向链），是**自驱**的（每一轮任务完成驱动一轮相生），是**螺旋上升**的（每轮循环都因传承殿的知识而更成熟）。

### 2.3 相生与相克（双重循环）

五行不仅相生，还相克。相生是演化动力，相克是平衡约束：

| 相克 | 工程语义 |
|------|---------|
| 木克土 | 功能生长受制于空间承载（不能无限加功能，受存储/架构限制） |
| 土克水 | 空间结构约束可能性流动（架构边界限制需求发散） |
| 水克火 | 可能性流动制约变革（新需求优先级可能推迟重构） |
| 火克金 | 变革冲击法则（重构时旧规则可能被打破） |
| 金克木 | 法则规范约束功能生长（规则限制不能乱加功能） |

生克并存 = 演化与稳定的动态平衡。

## 三、六道轮回结构循环

### 3.1 六道 ↔ 六层 映射

```
根(天道) → 域(人道) → 府(阿修罗道) → 殿(畜生道) → 阁(饿鬼道) → 园(地狱道)
  ↑                                                                      ↓
  └────────────── 园的产出反馈到根，开启新轮回 ──────────────────────┘
```

| 层 | 六道 | 工程语义 | 轮回特性 |
|----|------|---------|---------|
| 根 | 天道 | 顶层分区（最抽象，理想态） | 目标清晰、边界明确 |
| 域 | 人道 | 语义分组（纯目录） | 现实中运作，法则约束 |
| 府 | 阿修罗道 | 独立编译单元（crate） | 竞争中运作，有福无德（功能强但需制衡） |
| 殿 | 畜生道 | 模块分区（门面） | 承载具体职责，劳作 |
| 阁 | 饿鬼道 | 功能分组（接口契约） | 永远不够——接口定义需求 |
| 园 | 地狱道 | 实现落点（文件夹，代码文件放园内） | 最沉重——代码数据全在此 |

### 3.2 轮回的本质：螺旋上升

六层不是死板的线性下降，而是**有出口的循环**。园（最具体）的产出反馈到根（最抽象），提炼新概念，开启新一轮轮回。

**例**：
```
第一轮：根(鸿蒙) → 域(基础设施) → 府(事件总线) → 殿(事件分发) → 阁(分发实现) → 园(分发核心.rs)
  园中发现事件推送有延迟问题 → 经验沉淀

第二轮：园的反馈 → 根层认识到"事件"需要拆分为"路由+持久化+推送"三个独立殿
  → 道韵层新增法则：事件推送必须异步，不允许阻塞
  → 新一轮六道轮回开始
```

每一轮轮回都比上一轮成熟——这就是"六道轮回"的工程意义：**不是重复，而是螺旋上升**。

## 四、九五至尊权力分布

### 4.1 九与五的分配

```
九根 = 五行本体五根 + 工程四根
       ↑ 权力核心      ↑ 支撑结构

五行本体五根（变更需最严格决策，影响系统本质）：
  太初、混沌、乾坤、道韵、量劫

工程四根（变更相对灵活，只是工具链）：
  鸿蒙（底层）、证道（验证）、道果（构建物）、传承殿（非代码集合地）
```

### 4.2 权力分布原则

| 根类别 | 变更决策 | 理由 |
|--------|---------|------|
| 五行本体五根 | 最严格（需人类终裁） | 影响系统本质，是权力核心 |
| 工程四根 | 相对灵活（可自主演化） | 只是支撑工具，可替换 |

**九为阳数之极**：九根构成世界底层根基，不可再分不可再增。
**五为阳数之中**：五行本体五根居中守正，是系统的权力中枢。

## 五、九根六层容灾结构

### 5.0 维度是分类树（核心理解）

维度不是抽象哲学标签，而是**文件系统的物理分类树**——它本质就是存储文件夹、文件位置。

- **写代码**：按代码的本质语义归入对应树——"存在、生长"的代码放太初，"空间、承载、稳定、展示"的前端代码放乾坤
- **找代码**：直接去对应树，只遍历相关子树，**避开不相关树**
- **避免乱搜索和噪音**：不需要全局搜索，精准定位，上下文干净

这就是"世界观与工程一体两面"的落地：维度既是世界观概念（太初=存在），又是工程分类树（存"存在生长"的代码）。二者不是分离的，而是同一个物理事实的两个侧面。

**代码归属规则**：五行本体五根承载**领域代码**（按本质语义归入），鸿蒙只承载**跨域共享的底层能力**（HTTP、日志、配置等所有维度都用得到的东西）。

### 5.1 结构总览

```
洪荒-世界/
├── 太初/          ← 木·存在层（任务引擎代码在此）
├── 混沌/          ← 水·可能层（事件引擎代码在此）
├── 乾坤/          ← 土·空间层（记忆引擎 + 前端展示代码在此）
├── 道韵/          ← 金·法则层（规则引擎代码在此）
├── 量劫/          ← 火·时间层（迭代引擎代码在此）
├── 鸿蒙/          ← 底层（HTTP/日志/配置等跨域共享能力）
├── 证道/          ← 验证类（测试与门禁）
├── 道果/          ← 统一构建物 + 临时物集中地（debug/会话状态/编译缓存，可整体重建）
└── 传承殿/        ← 所有非代码的集合地（文档域放文档，其他域分类存放数据/资源等）
```

### 5.2 六层职责与容灾机制

| 层 | 职责 | 是否放代码 | 容灾机制 |
|----|------|-----------|---------|
| 根 | 顶层分区 | 否（纯目录） | 9根固定，AI 不可增删根 |
| 域 | 语义分组 | 否（纯目录） | 域内府数不限，删域需决策 |
| 府 | 独立编译单元（crate，插件） | 是（含 Cargo.toml） | 府可独立替换，删府=丢一个能力模块 |
| 殿 | 模块分区（门面） | 否（纯目录） | 殿 ≤ 6阁（硬约束，超限必须切割），删殿只丢模块分区 |
| 阁 | 功能分组（接口契约） | 是（trait 定义/接口） | 阁 ≤ 4园（硬约束，超限必须切割），删阁丢接口契约 |
| 园 | 实现落点 | 是（文件夹，代码文件放园内） | 园是爆炸半径最小单元，删园只丢一个实现 |

### 5.3 容灾设计的五个动机（用户明确）

1. **分类树定位，避免乱搜索**：代码按语义归入对应树，查找时只遍历相关子树，避开不相关树，杜绝全局搜索的噪音
2. **控制爆炸半径**：代码只落在园，AI 误删最多删一个园（几个文件），不会"一炸炸一片"删掉整个维度
3. **方便查找**：殿、阁子节点数量受控（殿≤6阁、阁≤4园，硬约束），府级不限，人类和 AI 都能快速定位
4. **人类看着好看 + AI 上下文噪音小**：层级清晰、数量受控，AI 读取时每个目录文件数有限，上下文干净
5. **可还原性**：小目录被删，事件流/记忆/决策记录中还有痕迹，能还原，不至于"炸完了什么都不记得"

### 5.4 府的可插拔（DSH 哲学落地）

- 府是**唯一编译单元（crate）**，通过 trait 定义跨府契约
- 府之间 `Arc<dyn Trait>` 解耦，生产路径注入真实实现，测试路径注入 mock
- 核心无特权：任何府都可被替换，不存在不可替换的核心

### 5.5 临时与非临时处置（道果 = 可整体重建的临时物集中地）

**核心判定**：凡可整体重建、无独立演化价值的产物，一律集中到道果；凡承载语义、需独立演化的内容，分布到 8 根 + 传承殿。

| 类别 | 归属 | 判定理由 |
|------|------|---------|
| debug 构建物 | 道果 | 可随时 clean 重建，无复用价值 |
| 会话临时状态 | 道果 | 一次会话的中间态，结束即失效 |
| 编译缓存 | 道果 | 可整体重建，clean 时一次性重生 |
| 领域代码 | 8 根（本体五根 + 鸿蒙） | 承载语义，独立演化 |
| 非代码内容 | 传承殿 | 文档/数据/资源的集合地 |

**道果的 clean 语义**：清理道果 = 整体重建，不损失任何语义；8 根与传承殿永远不因 clean 而丢失。

### 5.6 层命名规则（沿用 E盘 格式，命名不承载五行语义）

沿用 E盘 的层命名格式，保证人眼可读、AI 可预测，但**命名纯表意，不强制绑定五行属性**——避免一层命名同时承载"语义 + 五行"双重含义而 overload。

| 层 | 命名格式 | 示例 |
|----|---------|------|
| 域 | 4字-域 | 基础设施-域 |
| 府 | 4字-府 | 事件总线-府 |
| 殿 | 2字-2字-殿 | 事件分发-殿 |
| 阁 | 2字-2字-阁 | 分发实现-阁 |
| 园 | 名字-类型-园 | 日志-模块-园 |

**设计意图**：五行语义由**根**承担（太初=木、量劫=火……），层命名只管表意，二者分工清晰、互不污染。

## 六、五行能力子系统

### 6.1 五个引擎

| 引擎 | 五行力 | 落位（本体根） | 职责 |
|------|--------|--------------|------|
| 任务引擎 | 木·生长力 | 太初 | 任务受理、任务从无到有的诞生 |
| 迭代引擎 | 火·转化力 | 量劫 | 迭代周期、版本演进、重构触发 |
| 记忆引擎 | 土·承载力 | 乾坤 | 上下文槽位、经验承载、知识沉淀 |
| 规则引擎 | 金·结构力 | 道韵 | 规则注册表、法则证伪、结构约束 |
| 事件引擎 | 水·流动力 | 混沌 | 事件流、数据流、可能性流动 |

**鸿蒙的定位**：只放跨域共享的底层能力——HTTP 服务、日志记录、配置管理、模型连接等所有维度都用得到的通用件。五行能力引擎的领域代码归入各自本体根，鸿蒙不承载领域逻辑。

### 6.2 引擎间的相生链

```
金生水：结构约束保证事件流的完整性（每个状态转换必入事件流，不可篡改）
水生木：事件流驱动新任务诞生（事件中涌现的需求催生新任务）
木生火：任务积累驱动迭代（任务完成积累经验，触发版本演进）
火生土：迭代产出沉淀为记忆（每次迭代的产出写入记忆库）
土生金：记忆强化结构约束（记忆中积累的经验反馈为规则）
```

## 七、完整生命周期循环

### 7.1 一轮任务的五行驱动

```
用户输入需求
  ↓
混沌(水) → 意图收敛，可能性流动 → 确切需求
  ↓
太初(木) → 需求定义任务，存在诞生 → 任务受理
  ↓
鸿蒙(工程) → 四角色接力（决策→设计→实现→验收）→ 代码产出
  ↓
证道(工程) → 验证与门禁 → 通过/驳回
  ↓
乾坤(土) → 产出沉淀为空间结构 → 界面呈现、代码落盘
  ↓
传承殿(工程) → 经验写入知识库 → 法则评估
  ↓
量劫(火) → 时间累积，触发迭代 → 版本演进
  ↓
道韵(金) → 经验收敛为法则 → 规则更新
  ↓
回到混沌(水) → 新法则打开新可能性 → 新一轮循环
```

### 7.2 大循环与小循环

- **五行大循环**（系统演化）：混沌→太初→量劫→乾坤→道韵→混沌，每一轮让系统更成熟
- **四角色小循环**（单任务执行）：决策→设计→实现→验收，由鸿蒙驱动单任务完成

小循环是鸿蒙的基础能力，大循环是无数小循环积累驱动的系统演化。两者并行不悖。

## 八、与 E盘 的差异对比

| 维度 | E盘 | F盘蓝图 |
|------|-----|---------|
| 五行 | 缺失 | 演化引擎（三层贯通：属性→维度→能力） |
| 五行↔五根映射 | 无 | 木=太初、火=量劫、土=乾坤、金=道韵、水=混沌 |
| 五行能力代码归属 | 全塞进鸿蒙，本体根空置 | 归入本体根，鸿蒙只放共享底层 |
| 六层 | 静态空间递进 | 六道轮回螺旋上升 |
| 九根依赖 | 单向线性（太初→道韵→量劫→混沌） | 闭合相生（太初→量劫→乾坤→道韵→混沌→太初） |
| 维度本质 | 抽象命名 | 分类树（存储分区、查找索引） |
| 结构骨架 | 根→域→府→殿→阁→园 | 保留（容灾性已验证） |
| 府的可插拔 | 有 | 保留（DSH 落地） |
| 世界观与工程 | 两张皮（术语分离） | 一体两面（概念直接承载语义） |
| 系统性质 | 静态治理机器 | 自驱演化活体 |
