# 交互流式化 · 落地设计（阶段一 + 阶段二）

> 定位：把「对话流 / 任务卡」现有的短轮询交互升级为 **SSE 长连接推送**，并把道祖对话（`/api/dev/chat`）升级为 **流式输出**，对齐 AG-UI 事件驱动范式，让实时过程体验达到「所见即所得」。

- 文档型：落地设计（实施契约）
- 版本：1.0
- 域：鸿蒙/基础能力-域（数据服务）〔原含 乾坤/界面呈现-域（对话流），该前端域已随 2026-09-11 前端一刀切移除〕
- 更新：2026-09-08

> **前端移除补注（2026-09-11）**：本文档中，**后端 SSE 传输**部分（3.1~3.4、4.1~4.3 的后端改动、第五节事件契约）已实施且仍有效；**前端对话流改动**部分（3.5、4.4 前端改动清单、第五节「消费方」、第六节验收方式、第八节顺序 1 与「文件级落点·前端」）随 2026-09-11「前端一刀切」重构移除，保留历史留档。对外消费方统一称「客户端」。

## 一、背景与目标

### 背景
项目已具备 AG-UI 范式的「事件流雏形」：后端有过程事件流（思考/工具调用/工具结果/任务答复）、增量游标、会话落盘双写与 Resume/Fork 检查点；前端门面页已有对话流与五行任务卡。**但传输层仍是「短轮询」**，且道祖对话是一次性整体返回，实时体验存在明显卡顿。

### 目标
1. 阶段一：任务过程（思考/工具/结果）与状态推进改为 SSE 长连接推送，删除前端双轮询（状态 3s + 过程 2s），事件到达即渲染。
2. 阶段二：道祖对话（`/api/dev/chat`）新增流式变体，回复以 `TEXT_MESSAGE_CONTENT` 增量逐段推送，打字机式渲染；任务卡在回复流结束后即时挂起并接续订阅过程流。
3. 两阶段均保留旧接口与回退路径，不破坏现有测试与旧客户端。

## 三、阶段一：传输层 SSE 事件推送

### 3.1 选型对比

| 方案 | 评述 | 结论 |
|---|---|---|
| SSE（`text/event-stream`） | 单工下行足够（本场景只有后端→前端）；浏览器 `EventSource` 自动重连；GET 放行免鉴权；axum 原生 `Sse` 支持 | ✅ 采用 |
| WebSocket | 双向需求（审批交互已有独立 POST 接口，无需走 WS）；需维护连接状态机 | 不采用 |
| 长轮询/短轮询 | 现状方案，2–3s 延迟 + 请求冗余 | 仅作降级路径保留 |

### 3.2 新增接口设计

#### `GET /api/dev/stream?since=N`（当前会话过程事件流）
- 响应头：`content-type: text/event-stream`、`cache-control: no-cache`、`connection: keep-alive`。
- 事件序列（沿用现有 `驱动过程事件` 字段，`data` 为单行 JSON）：

```
data: {"序号":12,"任务id":3,"角色":"圣人","轮次":1,"类型":"思考","工具名":"","内容":"分析需求…","时间":1720000000}

data: {"序号":13,"任务id":3,"角色":"圣人","轮次":1,"类型":"工具调用","工具名":"编辑文件","内容":"{…}","时间":1720000000}
```

- 心跳：`sse::Event` 空数据注释行，每 **15s** 一条，保持代理连接不超时。
- 边界：连接不随单轮运行结束而关闭（空闲时仅心跳）；前端以阶段事件（完成/空闲/错误）判断本轮结束。

#### `GET /api/dev/stream/state?since=N`（阶段事件流）
- 同构：推送 `驱动阶段事件`（空闲/阶段完成/错误），复用 `驱动事件增量(since)`。
- 前端用它驱动五行任务卡状态位与顶部「运行中/空闲」徽章。

> 也可合并为单端点：`GET /api/dev/stream` 同时推两类事件，用 `驱动过程事件` / `驱动阶段事件` 结构区分。实现时二选一，文档以双端点为准（职责清晰）。

### 3.3 推送实现策略

现有缓冲为 `Mutex<Vec>` + 序号游标，**保持结构不变**，SSE handler 采用「增量轮询 + 心跳」：

- handler 每 **300ms** 调 `过程事件增量(since)` / `驱动事件增量(since)`，有增量立即批量发送并推进本地游标，无则发心跳后继续。
- 不引入新通道，行为即 SSE；延迟从 2s 降到 ≤0.3s。
- **后续演进**（不阻塞本阶段）：在 `记录过程事件` 处加 `tokio::sync::broadcast` 广播，handler 直接订阅同一通道，延迟降到亚毫秒级。列为可选优化，见第七节。

## 四、阶段二：道祖对话流式化

### 4.1 现状与差距

- `/api/dev/chat` 在接待锁内**整体等待 LLM** 返回（[受理处理.rs L165-174](../../鸿蒙/基础能力-域/数据服务-府/请求处理-殿/开发受理-阁/受理-处理-园/受理处理.rs#L165-L174)），前端要等完整回复才渲染，首屏「道祖静默」时间 = LLM 全输出时长。
- `hm_content_contract` 的 `生成`/`对话` 均为同步接口；`对话生成器` 与 `LLM池` 只发单次请求。
- 供应商（deepseek / minimax）均支持流式输出（`stream=true` + SSE 增量），缺的只是契约与实现。

### 4.2 目标形态

新增 `POST /api/dev/chat/stream`（请求体同 `/api/dev/chat`），响应为 SSE，事件序列（AG-UI 化）：

```
data: {"type":"RUN_STARTED","会话阶段":"接待中"}

data: {"type":"TEXT_MESSAGE_CONTENT","delta":"好的，"}
data: {"type":"TEXT_MESSAGE_CONTENT","delta":"我来安排这个需求…"}

data: {"type":"TEXT_MESSAGE_END"}
data: {"type":"RUN_FINISHED","阶段":"接待中","需求":null,"任务id":3}
```

- `任务id` 仅在道祖对齐并自动发布任务时非空（复用现有 `确认发布对齐需求` 逻辑，含「驱动台忙→需求保留」分支）。
- 旧 `POST /api/dev/chat` **保持不动**（兼容旧客户端与证道测试）。

### 4.3 后端改动清单

**① 内容契约新增流式接口**（鸿蒙/基础契约-域/内容契约-府）

```rust
/// 流式内容生成契约：回调式增量推送，兼容池故障转移与同步封装。
pub trait 流式生成器: Send + Sync {
    fn 生成流式(
        &self,
        提示词: String,
        on_chunk: &mut dyn FnMut(String) -> Result<(), hm_error::Error>,
    ) -> Result<(), hm_error::Error>;
}
```

**② 同步 → 流式适配**
- [生成模块.rs](../../鸿蒙/基础能力-域/内容生成-府/生成实现-殿/对话生成-阁/生成-模块-园/生成模块.rs)：`对话生成器` 新增 `流式生成器` 实现——单次流式请求解析 SSE（`data:` 行 → `on_chunk`）。若供应商不支持流式，退化为一次 `on_chunk` 全量回调。
- [池模块.rs](../../鸿蒙/基础能力-域/内容生成-府/生成实现-殿/对话生成-阁/池-模块-园/池模块.rs)：`LLM池` 新增 `流式生成器`——选中供应商流式，失败按配置故障转移到下一家；末家失败报错。
- （同步 trait 不动，避免波及 `工具对话器`/`内容生成器` 现有实现。）

**③ 道祖接待流式化**（[接待模块.rs](../../鸿蒙/系统装配-域/自主开发-府/接待驱动-殿/澄清对话-阁/接待-模块-园/接待模块.rs)）
- 新增 `接待流式(&self, 用户消息, on_chunk) -> Result<接待流式结果>`：**先释放会话锁、后流式回调**（避免持锁阻塞其他请求）；结尾返回 `{阶段, 需求, 任务id}` 供接口层收尾。
- 现有 `接待()` 保留，作为非流式路径。

**④ 接口层**（[受理处理.rs](../../鸿蒙/基础能力-域/数据服务-府/请求处理-殿/开发受理-阁/受理-处理-园/受理处理.rs)）
- 新增 `道祖对话流式接口`：`Sse` 返回；先发 `RUN_STARTED`，流式回调逐段发 `TEXT_MESSAGE_CONTENT`；LLM 完成后进入「对齐→发布」后处理（复用 `确认发布对齐需求`），最后发 `TEXT_MESSAGE_END` + `RUN_FINISHED`。
- 路由注册：`POST /api/dev/chat/stream`（post，走鉴权层，与 `/api/dev/chat` 同级）。

### 4.4 前端改动清单（[对话流.js](../../乾坤/界面呈现-域/门面承载-府/功能组件-殿/对话流-阁/对话-组件-园/对话流.js)）

| 改动点 | 说明 |
|---|---|
| 发送改用 `fetch` 流 | `EventSource` 仅支持 GET；POST 流式用 `fetch` + `ReadableStream` 按 `\n\n` 分帧解析 SSE |
| 打字机渲染 | 每帧 `TEXT_MESSAGE_CONTENT.delta` 追加到当前回复气泡文本节点（只 `textContent` 追加，避免重复 HTML 转义开销） |
| 收尾 | `TEXT_MESSAGE_END` 停止 loading 占位；`RUN_FINISHED.任务id` 非空 → `建任务卡` + `订阅过程流/阶段流`（与阶段一衔接） |
| 降级 | `fetch` 流失败或后端无该端点（404/415）→ 回退原 `POST /api/dev/chat` 整体返回 |

### 4.5 阶段二要点

- 流式回复不受「内容截断 200 字符」影响（该截断仅作用于过程事件的工具结果）。
- 接待锁释放时序是本阶段核心风险，见第七节「风险 4」。

## 五、事件契约总表（阶段一 + 二）

| 事件 | 来源 | 关键字段 | 消费方 |
|---|---|---|---|
| RUN_STARTED | chat/stream 首帧 | 会话阶段 | 对话流（清 loading 前置） |
| TEXT_MESSAGE_CONTENT | chat/stream · delta | delta | 对话流（打字机追加） |
| TEXT_MESSAGE_END | chat/stream 回答完 | — | 对话流（停 loading） |
| RUN_FINISHED | chat/stream 收尾 | 阶段/需求/任务id | 对话流（建任务卡/降级提示） |
| 过程事件（思考/工具调用/工具结果/任务答复） | /api/dev/stream | 序号/任务id/角色/轮次/类型/工具名/内容/时间 | 任务卡 `.过程` |
| 阶段事件（空闲/阶段完成/错误） | /api/dev/stream/state | 序号/类型/新状态/层级/角色 | 任务卡阶段位 + 顶徽章 |

**词表约定**：本阶段保留中文类型词（与现有存储/测试一致）；AG-UI 标准词映射（`思考→REASONING_*` 等）列为阶段三，不改存储结构即可由前端渲染层完成映射。

## 七、风险与降级

| 风险 | 等级 | 对策 |
|---|---|---|
| 1. 代理缓冲 SSE（nginx 等会攒包） | 中 | 生产建议关 `X-Accel-Buffering` / `proxy_buffering off`；心跳 15s 防超时 |
| 2. EventSource 不能带 Authorization 头 | 低 | 现有鉴权层 GET 放行，SSE 天然可用；如需鉴权改用 session cookie |
| 3. 供应商不支持流式 | 低 | `流式生成器` 实现层退化为单块回调；池故障转移兜底 |
| 4. 接待会话锁阻塞流式 | 中 | `接待流式` 先出锁再回调；维护 `接待()` 同步路径兜底 |
| 5. 断线续传 | 低 | 前端维护 `last序号` / `since`，重连时续传；`EventSource` 自动重连 |
| 6. 多客户端并发订阅 | 低 | 双端点按需推增量，环形缓冲天然并发安全（Mutex + 原子序号） |
| 7.【可选演进】缓冲轮询开销 | 低 | 后续改 `broadcast` 通道订阅，去除 300ms 内部轮询 |

## 八、实施顺序与落点

### 顺序
1. **阶段一（独立可验收）**：后端 SSE 双端点 → 前端订阅替换双轮询 → 门面页手动驱动验收。
