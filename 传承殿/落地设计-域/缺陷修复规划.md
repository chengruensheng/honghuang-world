## 一、修复原则

1. **按价值与风险排序**：先修「语义性核心断点」（认知底座接通），再修「规则硬违规」（错误处理/规模/命名），最后做「长期方向」。
2. **每阶段独立可交付**：一个阶段 = 一个可验证闭环（测试全绿 + 门禁全 PASS + 文档同步），不跨阶段混改。
3. **不破坏既有行为**：重构前跑测试，重构后测试全绿 + 重复率下降。
4. **严格走设计表/核对表**：每阶段开工前出设计表（本规划 + 阶段设计表），完成后出核对表存档。
5. **命名规则铁律**：新增产物全中文命名；涉及目录/文件重命名时同步更新 crate 依赖、模块.rs 汇总、架构全览图。

## 三、阶段 0A：认知提炼 + 检索接入（P0）

### 目标
让 2 个无状态执行器在生产链路生效，使三态认知从「能建图谱」迈入「能提炼 + 能检索」。

### 已核实的接入事实
- `心智地图::新()` 默认预置 **36 个空格位**（摘要空、可信度 0）；6 维度×6 格位名固定。
- `规则提炼器.提炼(&图谱)` 产出 4 个候选摘要，其格位名（外在·结构/依赖、执行·技术栈/工具）**与 36 格位清单完全匹配**。
- `检索器::新(图谱,心智,上下文).检索(问题)` 是无状态借用结构，即时构造，返回三态检索决策记录。
- 桥接模块 `装配带持久化` 在建图（line 145-163）后**未调用提炼器**；`认知注入` 仅有 推/拉/流 注入，**未用检索器**。
- 认知处理.rs 三 API **代码已返回真实数据**（从 `数据服务状态` clone），仅注释「当前为空结构」过时。

### 范围
1. 桥接模块建图成功后调用 `规则提炼器.提炼(&图)`，把 4 个候选摘要写入心智地图对应格位（外在·结构/依赖、执行·技术栈/工具），并 `tracing::info!` 记录提炼结果数。
2. `认知注入` 新增 `检索注入(问题) -> String`：内部构造检索器执行检索，返回三态检索答复文本；智能体循环「初始注入」把检索答复作为第三段（【检索·答复】）。
3. 修正认知处理.rs 三接口过时注释（「当前为空结构」→「返回运行时三态真实数据」）。

### 非目标（本阶段明确不做）
- 不接 LLM 池（阶段 0C）。
- 不改压缩器/纠错引擎接入（阶段 0B）。
- 不重构执行器生命周期结构（沿用借用式 + 即时构造）。
- 不重命名、不拆分文件（阶段 2/3）。

### 验收要点
1. 建图后「外在·结构」格位摘要含「项目共 N 个模块」；「执行·工具」格位摘要含 serde/tokio 等命中项。
2. 检索一个已知模块名（如「任务」）返回「图谱查询：涉及模块…」；三态全空返回诚实兜底。
3. `/api/cognition/cells` 返回的格位含提炼后的非空摘要（客户端可读到）。

### 风险
- 低：提炼器/检索器均纯机械、零网络、可重现；不改公开签名，仅新增调用点。

### 详细设计表
见 `.codeartsdoer/tasks/20260906_认知底座接通_设计表.md`。

### 实施状态
✅ 已实施（2026-09-06，v1.48）——桥接提炼填格位 + 检索注入 + 循环接线 + 认知 API 注释修正，全量测试 298→305 全绿，cargo build 零警告；核对表见 `.codeartsdoer/tasks/20260906_认知底座接通_核对表.md`。

## 四、阶段 0B：压缩 + 纠错接入（P0）

### 目标
让 2 个有状态执行器（压缩器/纠错引擎）在生产链路生效。

### 关键难点与方案
二者当前是**借用式结构**（`&'a mut 上下文` / `&'a mut 心智`），无法直接塞入 `Arc<Mutex>` 长期持有。需二选一（阶段 0B 开工前在各自设计表中敲定）：

- **方案甲（推荐）**：把触发逻辑内联进现有句柄——`认知注入.记录()` 追加消息后检查 `上下文.长度() ≥ 阈值` 时，在锁内即时构造 `压缩器` 执行一次 `手动压缩`；心智写入点（图谱校准 `校准候选格位` 下调置信度时）即时构造 `纠错引擎.纠正` 记录纠错事件。执行器保持借用式，无生命周期重构。
- **方案乙**：将压缩器/纠错引擎改造为持有 `Arc<Mutex<...>>` 的所有权长期结构，作为认知三态的第 4/5 个共享句柄。改动大、风险高，仅在甲方案无法覆盖「跨轮累计」需求时采用。

### 范围（方案甲）
1. `认知注入.记录()`：追加后若长度达 `上下文压缩阈值`（100）触发 `压缩器::手动压缩`，晋升记录 `tracing::info!`。
2. 心智写入点：图谱校准下调置信度、或新摘要与旧摘要冲突时，构造 `纠错引擎.纠正`，事件序列写回三态存储。
3. 新增测试覆盖「阈值触发压缩」「纠错事件生成」。

### 非目标
- 不接 LLM（阶段 0C）；不做跨会话蒸馏的持久化模式计数（除非方案乙）。

### 验收要点
1. 连续记录 100 条消息后，上下文被压缩为「[压缩摘要] + 最近 20 条」，长度下降。
2. 图谱校准后产生「纠错事件」记录，且受影响格位置信度降至 0.7。
3. 压缩/纠错后三态仍可 `保存` 落盘、`加载` 恢复。

### 风险
- 中：锁顺序必须严格 图谱→心智→上下文（沿用认知注入约定），短锁不跨锁，避免死锁。

## 六、阶段 1：错误处理治理（P1）

### 目标
清零 16 处静默吞错 + 1 处裸 unwrap + 5 处绝对路径。

### 范围
1. **16 处 `let _ =` 非豁免吞错** → 统一 `tracing::warn!("{操作}失败: {e}")`；关键状态写入（纠错/检索的心智写入）改 `?` 或至少 warn。文件：纠错闭环.rs(3)、驱动模块.rs(3)、池模块.rs(3)、执行模块.rs(3)、异步模块.rs(1)、驱动调度.rs(1)、检索决策.rs(1)、接待模块.rs(1)。
2. **1 处裸 unwrap**：`总线模块.rs:42` `subscribers.lock().unwrap()` → `.expect("总线订阅锁中毒")`。
3. **5 处绝对路径**：生产注释 2 处改相对描述；测试 3 处改临时目录（`std::env::temp_dir()` 拼接）或保留（测试专用但消除盘符依赖）。

### 验收
门禁 ③⑧ 全 PASS；`cargo test` 全绿；生产代码 `let _ =` 仅剩豁免项（remove_file/dotenv/recv/send）。

## 八、阶段 3：命名规范治理（P3）

### 目标
收敛英文命名与中英混杂标识符。

### 范围
1. **英文命名**：`rust-扫描-园`→`rust扫描`改中文（如 `扫描器-模块-园` 需评估 crate 依赖）；`.codebuddy` 工具目录保留。（原列出的 `桌面封装-府/src-tauri` 一项随 2026-09-11 前端一刀切移除，不再存在。）
2. **英文结构体名（29）+ 字段混杂（9）**：`Task/Iteration/Context` 等对外契约字段 `id/title/status/created_at` → 中文语义名（`标识/标题/状态/创建时间`）。**注意**：字段名序列化时若用于对外 JSON/TOML 契约，重命名会破坏序列化兼容，需 `#[serde(rename)]` 保持兼容或统一契约后同步所有调用点。
3. **语义重复（~36 组）**：优先修「下级＝直接上级」（证道 10 对府↔阁同名）与「跨目录同名 8 组」，按去后缀唯一性重命名。

### 风险
- 高：英文标识符透传是**全项目系统性风格问题**，涉及序列化契约与跨 crate 调用，需分 crate 逐个收敛，且每步跑全量测试。

## 十、风险与回滚总则

| 风险 | 缓解 |
|------|------|
| 目录/字段重命名破坏编译 | 逐层改 + `cargo build` 零警告 + `cargo test` 全绿后再进下一层 |
| 执行器接入引入死锁 | 锁顺序固定 图谱→心智→上下文，短锁不跨锁 |
| 认知 API 语义变化影响客户端 | 客户端同步消费返回体，冒烟验证空态→有数据 |
| 序列化兼容破坏 | 契约字段重命名用 `#[serde(rename)]` 保持旧 JSON 兼容 |

**回滚**：每阶段一个 git 提交点，出现回归 `git checkout` 回退该阶段，不影响其他阶段。
