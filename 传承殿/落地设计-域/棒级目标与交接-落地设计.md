# 棒级目标与交接 · 落地设计

> 定位：让「一次会话 = 若干棒、每棒有目标、棒与棒之间有交接」这件事在界面上**看得见**。
> 本文只解决「把真实关系讲清楚」，**不引入「目标逐棒传递」的新机制**（理由见第九节）。

- 文档型：落地设计（实施契约）
- 版本：1.0
- 域：乾坤/观星呈现-域（呈现层）+ 鸿蒙/基础能力-域（数据服务·驱动处理 / AG-UI 适配器）
- 更新：2026-09-11

---

## 一、诉求与结论

### 诉求（用户原话整理）

> 整个会话为「世界」，每个角色为「任务」——开始前显示本次目标（如「探索哪里哪里」），
> 结束后显示下一步目标；换角色后靠这个联系组建任务链。长期产出后还能根据项目进度展示的这些进行定位。

### 结论

1. **方向成立，但当前只兑现了一半**：终端要的「目标链」，其**契约早已在演示语料里签好**——
   `RUN_STARTED.input`（本次目标）、`RUN_FINISHED.result`（交出什么）、`STATE_DELTA`（状态流转到下一步）
   三样样例俱全；而**实时适配器一样都没实现**（详见 2.3）。本次工程的主体是**补齐欠账**，不是新造机制。
2. **不采用「世界 / 任务」这两个词**（详见第四节）：两者在本项目均已被占用，照搬会撞名。
3. **不引入「上一棒的目标成为下一棒的目标」这一机制**（详见第九节）：当前每层读到的是
   「同一份任务书 + 全部前序文档」，信息比「只接上一棒的目标」更充分；改成传递链会让界面更像链条，
   但系统未必更好，且要改五层产出契约。
4. **「任务链」不必新造——看板就是它的权威源**（详见 2.4）。看板自述为「五层协作的唯一通道」；
   同一 `task.id` 一路流转（`待圣人设计 → 圣人设计中 → 待大罗金仙实现 → …`，不新建任务），
   `承接历史`（角色接力链）+ `状态历史`（流转史）+ `层级历史`（每层产物）已完整落盘、可看可溯。
   天机视图**唯一缺的是「棒 ↔ 看板任务」的锚点**：事件流里 `任务id` 已有却未透传（5.1）。
   补上它，目标（任务标题）与下一步（新状态）都自动可追到看板。

## 二、现状事实（只读依据）

### 2.1 数据源盘点

| 界面想要的信息 | 现有位置 | 现状 |

| 会话 id | `threadId` / `runId` 中段（`run-1789108486752-3` 中段为毫秒时间戳）；`GET /api/dev/sessions` | ✅ 有 |
| **任务 id** | `驱动过程事件.任务id`（`事件.rs:47`）、`驱动阶段事件.任务id`（`事件.rs:11`） | ⚠️ **有，但 AG-UI 适配时未透传** |
| 任务标题 / 描述 | `GET /api/board`（全量）、`GET /api/board/{id}`（单个，`看板处理.rs:132`）；前端 `拉看板()` 已消费 | ✅ 有；**缺的只是事件流不带任务号**（5.1） |
| 本棒角色 | 每帧注入的 `角色` 字段（`驱动处理.rs:286-288`、`322-324`） | ✅ 有 |
| 本棒阶段名 | `STEP_STARTED`（适配器**从不发**）；演示语料有 | ❌ 实时缺 |
| **下一步（新状态）** | `驱动阶段事件.新状态`（如「待大罗金仙实现」） | ⚠️ **有，却被塞进 `STEP_FINISHED.step_name`（语义错位）** |

| 产出物名 | `RUN_FINISHED.result = None`（`协议适配.rs:136`） | ❌ 无 |
| 每棒的任务书（目标） | `RUN_STARTED.input = None`（`协议适配.rs:45`） | ❌ 无 |

### 2.2 三处真缺陷（真实浏览器实测，端口 8321）

| # | 现象（证据） | 根因 |
|---|---|---|
| D1 | 14 根棒的终态语**全部是兜底语「已交接下一棒」**，真实的「待大罗金仙实现」一条都没留下 | 过程流与阶段流是**两条独立 SSE**，收尾帧到达时该棒已被下一个 `RUN_STARTED` 的兜底收尾（`帧编排.js:57`）；此后 `取待收尾棒` 找不到未完成的棒，真实终态被暂存进 `运行时.待收尾` 后**永不取用** |
| D2 | 所有棒的 `.棒名` **全为空** | 实时适配器不发 `STEP_STARTED`，而棒名只由它写入（`帧编排.js:80-84`） |
| D3 | `STEP_FINISHED.step_name` 在**演示与实时下语义不同**：演示是「圣人 · 设计」（步骤名），实时是「待大罗金仙实现」（**新状态名**） | `协议适配.rs:131` 把「新状态」当成了 stepName；阶段条（`显阶段`）因此显示「清理完成」这一类状态名而非阶段名 |

### 2.3 契约欠账：演示语料 vs 实时实现

演示语料（`演示语料.js`，标注为「契约样例」）与实时适配器逐条对照：

| 契约要素 | 演示语料（应然） | 实时适配器（实然） |
|---|---|---|
| `RUN_STARTED.input` | `{任务id:31, 角色:"圣人"}` | `None` |
| `RUN_FINISHED.result` | `{新状态:"待大罗金仙实现", 产出:"设计文档"}` | `None`，且**只在会话空闲发一次**（演示是每棒一条） |
| `STATE_DELTA` | `[{op:"replace", path:"/任务/31/status", value:"待大罗金仙实现"}]` | **一条都不发** |
| `STEP_STARTED` | 有（`stepName:"圣人 · 设计"`） | **从不发** |
| `STEP_FINISHED.stepName` | `"圣人 · 设计"`（阶段名） | `"待大罗金仙实现"`（新状态名，语义错位） |

> 结论：**演示语料是「应有的契约」，实时适配器是欠账方**。本次以后者为改对象，尽量不迁就前者（唯一例外见 5.4）。

### 2.4 看板即任务链（现有权威源，无需新造）

用户的判断成立：**「任务链」的载体不是要新建的东西，看板一直在提供它**。

| 链路要素 | 看板中的现成位置 |
|---|---|
| 任务名（本次目标） | `Task.title`（发布时即定，用户原文） |
| 下一步（交接） | `Task.status` 流转（`TaskStatus`，由 `执行推进()` 校验 `可流转到` 后写入） |
| 谁做过（接力链） | `Task.承接历史: Vec<AgentRole>`（看板卡「承接」行：`圣人 → 大罗金仙 → …`） |
| 怎么走到这一步 | `Task.状态历史: Vec<StatusChange{原状态,新状态,操作者,时间,备注}>`（看板卡「动态」行） |
| 每层产物/耗时 | `Task.层级历史: Vec<层级记录>`（开始/完成/产物/回退） |
| 唯一可追溯 | `Task.任务标识`（UUID + 时间戳） |

- 写入时机 = 用户说的「登记」：`提交任务()` → `执行推进()` 落 `状态历史` → `保存()` 写 JSONL。
- 读取入口：`GET /api/board`（全量，`看板渲染.js::拉看板()` 已消费）、`GET /api/board/{id}`（单个）。
- 前端**已有**「按任务号拉看板」的先例：`接待逻辑.js:60` —— `if(ev.任务id) 广播(总线.请求拉看板)`。

**「分级」的对照**：设想中的「会话 → 角色 → 目标」三级，在本项目即
**会话 → 棒（角色的一段任期）→ 任务书（看板 `Task`）**：

| 设想 | 本项目对应 | 说明 |
|---|---|---|
| 整个会话为「世界」 | **会话**（`threadId`） | 「世界」已被项目名与 `项目认知-府/世界模型-殿` 占用（第四节） |
| 每个角色为一个「任务」 | **一次 run = 一根棒** | 「任务」已被看板 `Task` 占用；且角色**不新建任务**——同一 `task.id` 一路流转 |
| 开始时显示任务目标 | 棒头「本次目标」（6.1） | 源 = 看板 `Task.title`（用户发布时即定） |
| 结束后显示下一步目标 | 棒头「→ 下一步」（6.2） | 源 = 状态机流转出的**新状态**，不是模型自述 |
| 下一角色以上一角色的「下一步目标」为任务目标 | 同一 `task.id` + 新 `status` | 看板本就如此：`待圣人设计 → 圣人设计中 → 待大罗金仙实现 → …` |
| 链条的起点 | **道祖接待**（用户登记的需求） | 链路源头是用户经道祖登记的需求，之后每一棒都是它的推进 |

> 关键差别：设想中说「**上一位角色给出**下一步目标」，而这套系统里「下一步」由
> **状态机**（`执行推进()` + `TaskStatus::可流转到`）决定，不由模型自出——正是这一点让目标
> 可追溯、不可臆造（原则 2）。「从道祖发」因此不只是流程规矩，也是这条链**可溯源的起点**；
> 且发布必须走道祖接待，`POST /api/board` 直发只驱动 1 轮，会误判成「发布了却没跑」（W7）。

> 因此本轮**不新建任何任务链设施**，只做一件事：**把事件的 `任务id` 透传到天机流**（5.1），
> 让「棒」能指向看板上那张卡（6.1 / 6.5）。

## 三、设计原则（硬约束）

1. **界面只画「阶段推进链」，不画「目标传递链」**。
   真实机制是「同一任务书 + 前序文档 + 角色固定职责」，不是「A 把目标交给 B」。
   界面若画成传递链，等于**替系统自述了一个不存在的机制**。
2. **目标必须来自权威源**。可用的权威源只有两处：喂给该层 LLM 的**任务书**（任务 #id / 标题 / 描述），
   与确定性状态机产出的**新状态**（`TaskStatus` 流转，非模型自述）。
   **禁止**拿模型推理草稿、模型自出的 JSON 字段当「目标」——那是草稿冒充契约。
3. **真信息可覆盖兜底语**。兜底语（「已交接下一棒」）是「我还没拿到真实终态」的占位；
   后到的真实终态必须能覆盖它。此条与「降级提示不可被覆盖」（`呈现域规则.md` 四·2）不冲突：
   那条防的是「故障说明被空态盖掉」，本条说的是「占位语遇到真话该让位」——**同样是真话优先**。
4. **取不到就不编**。任务标题在历史回放时可能已不在看板，此时**只显示任务号**，不得回退成猜测文本。

## 四、层级定名（不采用「世界 / 任务」）

| 用户用词 | 冲突 | 本项目采用 |
|---|---|---|
| 世界 | 项目名「洪荒·世界」；`项目认知-府/世界模型-殿` 已占用 | **会话**（`threadId`，接口 `/api/dev/sessions` 已存在） |
| 任务 | 看板任务（任务 #31）、`任务管理-域/任务核心-府/任务模型-殿` 已占用 | **棒**（既有术语：一次 run = 一个角色的一段任期） |

## 五、后端变更

改动集中在**适配器与透传**两处，**不动内部事件结构、不动驱动机制**（符合「适配器映射、非破坏」既有策略）。

### 5.1 透传任务号（`驱动处理.rs`）

过程流 AG-UI 循环（`驱动处理.rs:281-291`）已有「注入角色」的先例，照此再加一行：

```rust
if let Some(任务id) = 事件.任务id {
    载荷json["任务id"] = serde_json::Value::from(任务id);
}
```

- 数据源现成（`驱动过程事件.任务id`），**无需改任何结构体**。
- 只对 `RUN_STARTED` 真正有意义，但统一注入不影响其它帧（前端按需取用）。
- 阶段流同理注入，供收尾帧定位（`驱动处理.rs:316-326`）。

### 5.2 修正 `STEP_FINISHED` 语义（`协议适配.rs:130-132`）

```
现状：StepFinished { step_name: 事件.新状态 }        // 状态名冒充步骤名
改为：StepFinished { step_name: "{角色} · {职责}" }   // 与演示语料一致
```

- `角色` 由 `事件.角色`（显示名）取，`职责` 取自 `AgentRole::职责`。
- **落点修正**：原计划「把 `驱动模块.rs` 的 `角色职责()` 提为 `pub(crate)`」不成立——适配器在
  `hm-http`，该函数在 `hm-agent`，跨 crate 提 `pub(crate)` 无用。职责是角色的属性，故**上移到
  `AgentRole::职责`**（`角色数据.rs`，`hm-cognition` 两个 crate 都已依赖），并同步给
  `驱动模块.rs` 的任务书提示词使用——一张表两处共用，才是真的不漂移。
- 事件流只带显示名，故同时补 `AgentRole::从名称()` 反查；`看板处理.rs` 原有的 `解析角色()`
  改为委托它，姓名表也归一处。
- 兜底：角色缺失或不在五层之列时 `step_name` 用「阶段」，保持非空（AG-UI 要求步骤名非空）。

### 5.3 补发 `STATE_DELTA`（`协议适配.rs` 阶段事件分支）

`驱动阶段事件` 的 `新状态` 正是 AG-UI `STATE_DELTA` 的语义，且**演示语料早就这么写了**：

```
"阶段完成" => vec![
    Event::StateDelta(StateDelta { delta: vec![json!({
        "op": "replace",
        "path": format!("/任务/{任务id}/status"),
        "value": 新状态,
    })]}),
    Event::StepFinished(...),   // 见 5.2
]
```

- **类型现状**：`hm_agui::StateDelta.delta` 是 `Vec<serde_json::Value>`（**没有** `JsonPatch` 结构体），
  故补丁用 `serde_json::json!` 就地构造，**不新增类型**。
- 取值条件：`任务id` 与 `新状态` 都在才发；缺任一就不发——补丁指向不了任务的状态，就是编的。
- 发送顺序 `STATE_DELTA` 先于 `STEP_FINISHED`：前端收尾时要读它作为「交出什么」。
- 前端已有消费分支（`帧编排.js`「状态」条），并新增「→ 下一步」位（见 6.2）。

### 5.4 暂不补 `RUN_FINISHED.result`（并修正演示语料）

- 实时语义下 `RUN_FINISHED` 表示「**整个会话**空闲」，**不是**「一棒结束」；而演示语料把它当「每棒一条」用。
  「一棒的结束」已由 5.2 的 `STEP_FINISHED` 表达，二者职责重叠。
- **决定**：`RUN_FINISHED` 保持 `result: None`；**演示语料改为只在五棒末尾发一条 `RUN_FINISHED`**，每棒的收尾改用 `STATE_DELTA + STEP_FINISHED`（语料里 STATE_DELTA 本来就有，正好承接）。
- 连带清理见第七节 W2。

### 5.5 不补 `STEP_STARTED`

「一棒开始」已由过程流的 `RUN_STARTED` 承担（角色一变即开棒），再发 `STEP_STARTED` 是冗余。
前端对 `STEP_STARTED` 的既有分支保留（演示语料仍用它），但**棒名不再依赖它**——改由「本次目标」占据该位置（见 6.1），正好补上 D2 的空位。

## 六、前端呈现

### 6.1 棒头：三段式

现状棒头：`[角色] [棒名(空)] [棒摘] [状态] [条数] [折叠符]`
改为：`[第N棒] [角色 · 职责] [本次目标] [→ 下一步] [状态] [条数]`

| 位 | 内容 | 数据源 |
|---|---|---|
| 第 N 棒 | 会话内序号（自增） | 前端按 `RUN_STARTED` 顺序 |
| 角色 · 职责 | 如「大罗金仙 · 实现」 | `事件.角色` + 前端 `职名()`（已有） |
| **本次目标** | 如「任务 #31 · 任务看板新增「挂起/恢复」状态」 | `RUN_STARTED.任务id` → 前端 `运行时.任务集`（`拉看板()` 已拉）取 `title`；未命中则按 id `fetch("/api/board/{id}")`；两者皆无（历史任务已不在看板）**只显示 `任务 #31`**，不编标题（原则 4） |
| **→ 下一步** | 如「→ 待准圣验收」 | `STATE_DELTA` 中 `path` 以 `/status` 结尾那条的 `value`（5.3）；无兜底，取不到就不显示（原则 4） |

- 「本次目标」占据当前空着的 `.棒名` 位（消化 D2，不新增行高）。
- `职名()` 现为「道祖 → 需求」，在**终审棒**上会读作「道祖 · 需求」（错位）——**本次不动**（既有映射问题，见 9.3）。

### 6.2 交接的显式化（棒头「→ 下一步」位）

棒头新增一位 `.棒交`，**收尾时**露面：`→ {新状态}`（如「→ 待准圣验收」「→ 清理完成」）。

- 数据源**唯一**是 5.3 的 `STATE_DELTA`（`path` 以 `/status` 结尾那条的 `value`）。
  5.2 之后 `STEP_FINISHED.stepName` 已是「角色 · 职责」，**不再是**新状态，故**取消**原先「缺
  `STATE_DELTA` 时退回 `stepName`」的兜底；取不到就不显示（原则 4）。
- 只在收尾时显示：任期内该任务的状态流转由棒身里的「状态」条如实列出，棒头再显示一遍会互相干扰。
- 措辞用「→」而不用「交给」——**新状态是状态机的确定性产物，不含"谁来接"的承诺**；
  下一位承接人由看板的承接历史决定，界面不替它承诺。

### 6.3 左栏轮标带目标

现轮标：`第 N 棒 · 角色 · 职责`（`对话渲染.js`）
改为：`第 N 棒 · 角色 · 职责 — {本次目标}`，让左栏的结论与右栏的棒**一眼对得上**，长会话下可定位。

### 6.4 修 D1：真信息覆盖兜底语（`帧编排.js`）

兜底语只在下述条件下写入，否则不覆盖已有终态：

1. 该棒**尚无终态**时，`RUN_STARTED` 带来的「已交接下一棒」正常写入；
2. 该棒终态**已是兜底语**、又收到该角色的真实 `STEP_FINISHED` / `RUN_FINISHED` 时，**允许覆盖**。

实现要点：`收尾棒()` 增加「可覆盖」判据（终态语是否为兜底语），**幂等性只对真实终态生效**。
不得放宽成「任何后到帧都能改写终态」——那会让乱序帧把已确定的终态改坏。

### 6.5 棒 ↔ 看板的锚点（溯源）

棒头的 `任务 #31` 与看板视图是**同一张卡**：点它切到看板视图并定位该任务（看板卡已有 `#id` / `承接` / `动态`）。

- 不需要新接口：天机视图与看板视图**共用** `运行时.任务集`（同一份 `拉看板()` 数据）。
- 分工：天机视图答「这一棒在做什么、交出了什么」；看板答「这个任务从哪来、走过谁、现在在哪」。
  两者指向同一 `task.id`，**互相可对号**——这正是「长期产出后按项目进度定位」的落点。
- 若任务号在看板暂无对应（历史回放），`#31` 仍显示但**不加链接**——取不到就不编（原则 4）。

## 九、明确不做（边界）

1. **不做「目标逐棒传递」机制**。当前每层读到「任务书 + 全部前序文档」，改为「只接上一棒的目标」是**信息削减**；
   且要让五层产出契约各加「下一步目标」字段，模型可能自出臆造目标——违背原则 2。
   看板已是权威链路（2.4），再叠一条传递链等于**两套真相**，迟早对不上。
2. **不做「世界 / 任务」两级容器**。命名撞车（第四节）；且「链」的可读性由 6.1–6.3 直接解决，
   未必要靠新容器。若后续仍要分组，另立设计。
3. **不修「道祖 · 需求」在终审棒上的错位**。属既有角色—职责映射问题，牵动 `职名()` 与多处署名，
   单独评估。
4. **不给「产出物名」找来源**。`驱动结果::阶段完成 { 任务id, 角色, 新状态 }` 不含产出物，
   要补需改驱动模块返回结构；而「交出了什么」已由棒头摘要（做了什么）表达，本轮不重复。
