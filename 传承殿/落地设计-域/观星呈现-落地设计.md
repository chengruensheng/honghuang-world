## 二、五层职责定义（对齐的是后端的「组织思想」）

后端五层角色（道祖→圣人→大罗金仙→准圣→太乙金仙）是一条**串行接力流程**，前端没有这条流程。前端对齐的是后端的**组织思想**：单一职责、层层汇总上报、插件化、依赖单向、同级不重复。

| 层 | 后端语义 | 前端职责 | 韧性语义 |
|----|---------|---------|---------|
| 域 | 唯一对外边界 | 呈现边界：统一装配各府、隔离故障 | 静态骨架先行 |
| 府 | 独立编译单元（插件） | **可插拔能力单元**：独立装载/卸载 | **故障隔离边界** |
| 殿 | 府内分区 | 能力内的职责分区 | 分区互不依赖 |
| 阁 | 具体功能 | 具体功能单元 | — |
| 园 | 落地实现文件 | 落地实现文件（代码落园） | — |

## 三、韧性设计（崩溃隔离）

### 3.1 三道防线

1. **静态骨架**——背景、顶栏、两栏栅格、看板容器写在 `index.html`，样式用 `<link>` 静态引入，不经过任何 JS。JS 全崩，骨架仍在，空的只是内容区。
2. **动态装载**——域装配各府时用 `await import()` 逐个加载，每次包 `try/catch`。某府加载失败或抛错，只在该区域显示降级提示，不拖垮其它府。
   （若用静态 `import`，一处语法错会让整条依赖链全挂，达不到隔离；故必须动态装载。）
3. **单向依赖**——府与府之间不互相 `import` 业务代码，只经「总线」（浏览器 CustomEvent）通信。依赖方向唯一：域装配 → 府 → 殿 → 阁 → 园。

### 3.2 崩溃影响面

| 崩掉的单元 | 用户看到什么 |
|---|---|
| 底座骨架（样式部分） | 样式丢失——几乎不可能（纯 CSS 静态引入，无 JS 依赖） |
| 底座骨架（运行时中枢部分） | 全局不可用——但它无网络、无异步、无渲染，风险最低 |
| 契约词表 | 各视图提示「契约未就绪」，骨架完好 |
| 观测台面 | 左右两栏空白，顶栏、看板照常可用 |
| 看板流转 | 看板页空白，观星台照常用 |
| 流式驱动 | 无实时数据，可切回演示模式，骨架完好 |

## 七、模块契约与依赖方向

- 各模块用 ES module `export` 显式暴露；运行时可变状态统一收敛在 `运行时中枢.js` 导出的**状态对象**上（`export let` 在跨模块赋值时不会同步，必须用对象承载）。
- 依赖方向（单向无环）：
  `装配入口 → 各府对外模块 → 运行时中枢 / 契约词表 / 演示语料`
- 被多处调用的公共函数一律下沉到 `运行时中枢.js`（`$`/`转义`/`连接语`/空态），杜绝各府各算一套。
- `帧编排.js` 单向依赖 `棒条渲染.js`/`变更渲染.js`/`摘要逻辑.js`；反向不成立。

1. `cargo test --workspace` 全绿（未动 Rust，纯回归确认）；

3. **中文路径资源加载**：`<link>`/`import()` 的中文路径经 URL 编码后 `ServeDir` 正确解析（本设计最大技术风险，须实测；不通过则资源文件名退回英文，按规则「非强制」例外处理）；
4. **韧性复验**：人为在某府注入错误，确认骨架与其它府不受影响、该区域显示降级提示。

|---|---|---|
| 观测台面 · 帧编排 | 看板流转 · 看板渲染 | `拉看板` |
| 观测台面 · 发布逻辑 | 看板流转 · 看板渲染 | `拉看板` |

（骨架硬约束不受影响：静态骨架 + 逐府 `try/catch` 已保证「背景布局不出问题」成立。）

`总线` 已预留 `请求拉看板` 事件但未启用。是否将上表前 3 处（纯查询、无返回值）改为总线广播，使「看板流转-府」成为真正可插拔，待定。
