## 一、项目结构

### 1.1 九根六层

所有代码按「维度 → 域 → 府 → 殿 → 阁 → 园」六层切分，**能力只在园落地**，中间层只放模块桥接（`模块.rs`，仅 `pub mod` 声明，不写实现）。

| 层 | 回答 | 承载 |
|:--|:--|:--|
| 维度 | 世界由什么构成 | 九根（本体 5 + 工程 4） |
| 域 | 靠什么活着 | 纯目录，无文件 |
| 府 | 什么能力 | lib crate（编译单位），`入口.rs` 聚合 |
| 殿 | 哪些模块 | `模块.rs` 桥接 |
| 阁 | 什么功能 | `模块.rs` 桥接 |
| 园 | 怎么实现 | 实现代码 + `模块.rs` 桥接 |

### 1.2 九根维度

| 类别 | 维度 | 对应 |
|:--|:--|:--|
| 本体五根（创世链） | 太初 | 存在 |
| | 混沌 | 可能性 |
| | 乾坤 | 空间（容器） |
| | 道韵 | 法则 |
| | 量劫 | 时间（劫数） |
| 工程四根（保障链） | 鸿蒙 | 地基（通用能力 + 插件基础设施） |
| | 证道 | 测试 |
| | 道果树 | 构建 |
| | 传承殿 | 传承 |

鸿蒙是唯一地基，承载通用能力（文件读写、网络、日志、密钥、缓存、事件总线、状态共享、模型连接等），同时是插件注册表 + 事件总线 + 状态共享的提供者。

### 1.3 府是插件单元

架构决策（2026-08-20 界主拍板）：**九是维度，府是插件**。

- 每个府是一个 lib crate，暴露 Service Definition（服务 trait，插件接口）。
- 跨府引用经插件注册表查找目标府的 Service Definition，止步于 lib 根，禁深链到殿/阁/园。
- 跨维经鸿蒙（插件注册表 + 事件总线 + 状态共享）中转，禁跨维直调。
- 新增能力只需写一个府插件，不必走完整六层。

## 二、常用命令

### 2.1 构建

```powershell
cargo build
```

构建产物统一落入 `道果树/构建物-域`（由 `.cargo/config.toml` 配置，不污染源码树）。

### 2.2 测试

```powershell
cargo test
```

当前状态（2026-08-21）：505 passed / 0 failed / 4 ignored。

### 2.3 格式检查与格式化

```powershell
cargo fmt --check          # 检查格式是否合规（不改文件）
cargo fmt                  # 自动格式化
```

### 2.4 静态检查

```powershell
cargo clippy               # 全 workspace clippy
cargo clippy -- -D warnings # 警告当错误
```

### 2.5 运行操作台

```powershell
cargo run -p mingling_fu --bin 号令
```

操作台是世界的入口，界主经此发布想法，世界自动走完整迭代链路。

### 2.6 单府操作

```powershell
cargo build -p shihai_fu          # 只构建识海承载-府
cargo test -p tianting_fu         # 只测天庭治理-府
cargo clippy -p daoshu_fu         # 只检查道术施展-府
```

## 三、开发流程

### 3.1 先入稿、再落码

新增设计（新府殿阁园、新业务逻辑、新机制）必须**先并入对应设计稿对应章节，再实现**。

- 层级结构 → `层级结构-设计.md`
- 心智模型 → `项目心智模型-设计稿.md`
- 多智能体架构 → `多智能体架构设计.md`
- 身脑融合决策 → `融合蓝图-设计稿.md`

实现须能在设计稿溯源，溯不到源视为补丁。设计稿随世界生长，不另立补丁文档。

### 3.2 日志埋点

日志已统一落地，勿重复实现：

- **技术日志**走 `鸿蒙/基础设施 - 域/日志记录-府`（lib = `rizhi_fu`，tracing 定制封装），各府经 lib 根调用。
- **业务流水**是领域数据，走识海承载-府（格位记录），两者勿混。

新增代码（新建府殿阁园、新增业务逻辑）时，必须主动把日志埋点跟上，统一经日志记录-府 lib 根调用，不得遗漏。

### 3.3 跨府引用

跨府引用经 Service Definition（插件接口），止步于 lib 根：

```rust
// ✓ 正例：经插件上下文查对方 Service Definition
use shihai_fu::识海服务;
let 服务 = ctx.查找服务::<Arc<dyn 识海服务>>()?.ok_or("未注册")?;
```

```rust
// ✗ 反例：深链到对方园内具体文件
use shihai_fu::某殿::某阁::某园::某函数;  // 禁止
```

### 3.4 跨维引用

跨维经鸿蒙中转，禁直调：

- 跨维事件 → 事件总线-府（`shijian_fu`）
- 跨维状态 → 状态共享-府（`zhuangtai_fu`）
- 跨府查找 → 插件承载-府（`chajian_fu`）

### 3.5 命名规范

- 全中文标识符，类型 UpperCamelCase，函数/变量 snake_case。
- 目录名用连字符（`文件-读写-殿`），Rust 模块名用下划线（`文件_读写_殿`），由 `#[path]` 桥接。
- 域/府 2 段，殿/阁/园 3 段；园名含实现手段词（流式/原子/批量/并行/缓存/降级/兜底…）。
- 严禁过度使用 AI 语气，命名和注释要朴实。

### 3.6 临时产物

临时测试、临时脚本、临时文档等放入根目录 `临时文件夹/`，任务结束后清空。该目录不进 git（已 .gitignore 排除）。

## 四、格位与图谱

### 4.1 格位（心智模型）

识海承载-府以 36 格位（日常）/ 72 格位（全量）组织记忆，六范畴分格位，每格位独立存储（`.jsonl` 文件，文件名 = 格位名）。

| 范畴 | 含义 | 代表格位 |
|:--|:--|:--|
| 目标 | 为什么做 | 初心·使命、任务、目标、验收标准 |
| 规则 | 不可破/可迭代约束 | 铁律·总纲、标准、细则·解读、架构 |
| 自我 | 操守与边界 | 价值观·原则、底线、身份、能力 |
| 程序 | 执行规则 | 环节规则、例外·临时 |
| 世界 | 事实状态 | 结构、文件、状态、环境·依赖 |
| 经历 | 已发生的事 | 事件、变更、产物、教训 |

检索按顺序三档排布：最前（核心：初心/铁律/身份/任务）→ 中间（背景：结构/文件/历史）→ 最后（当前：目标/进度/验收结果）。预算不足时从中间往两头裁。

当前格位健康（2026-08-21）：25 个 jsonl 文件全健康。

### 4.2 依赖图

识海承载-府维护依赖图（符号档案 + 结构树），供现状装配、跨文件追溯、契约投影。

- 符号档案：函数/类型/接口的签名与定义体。
- 结构树：目录与模块的组织。
- 查询：`查模块`、`查文件`、`查库根导出`、`查测试样例`。

当前图谱健康（2026-08-21）：862 符号 / 429 边 / 0 孤儿。

### 4.3 注入规则

可操作规则（如全中文输出纪律）存入 `细则·解读` 格位，拼装提示词时作为固定高价值信息注入，不硬编码在模板里。

- 主机制：`元数据层化` 拼完首屏后追加「固定规则段」，遍历范畴=规则的中间档格位。
- 补充机制：`shihai_fu::注入规则(存储, "细则·解读")` 读格位链头注入，供独立构造提示的角色按需接入。

已五处接入（2026-08-21 落码）：终裁单准圣审验、终裁鸿钧终裁、要求化解析想法、模板生成设计/改稿、教训归因归因。

## 六、新增府/角色/工具的步骤

> 本节对应 §14.12 cookbook 总纲定位：新增府/角色/工具的步骤。

### 6.1 新增府（插件）

1. **入稿**：在 `层级结构-设计.md` 对应维度章节落笔新府的域/府/殿/阁/园切分。
2. **建目录**：按六层规范创建目录，域纯目录无文件，府放 `入口.rs`，殿/阁/园放 `模块.rs` 桥接。
3. **建 crate**：新府目录下建 `Cargo.toml`，`lib.path` 指向 `入口.rs`；根 `Cargo.toml` 的 `members` 加新府路径。
4. **Service Definition**：在 lib 根定义服务 trait（插件接口），`应用()` 方法中创建服务实例注册到插件上下文。
5. **落码**：园内实现文件承载代码，经 `模块.rs` 逐层 `pub use` 透出到 lib 根。
6. **日志埋点**：经 `rizhi_fu` lib 根调用，跟上埋点。
7. **测试**：在 `zhengdao_fu` 对应殿补黑盒测试。
8. **核验**：`cargo build && cargo test && cargo clippy` 全绿。

### 6.2 新增角色

1. **入稿**：在 `多智能体架构设计.md` 角色章节落笔角色定位与工作流。
2. **角色册**：经世界「记忆 回填」写入角色册配置（或界主直接录入）。
3. **道术**：若需新道术，在道术施展-府对应园落码。
4. **核验**：`号令 装配 检查` 确认角色注册状态。

### 6.3 新增工具

1. **入稿**：在 `多智能体架构设计.md` 工具章节落笔工具契约。
2. **落码**：道术施展-府 手脚工具集对应园落码，经 lib 根透出。
3. **权限**：工具清单按角色过滤可见工具，配置权限。
4. **核验**：`cargo test` 确认工具调用回路。

## 七、常见问题排查

### 7.1 编译错误四类

实测高频编译错误：

1. **函数作用域**：函数定义在错的模块或未 `pub use` 透出 → 查 lib 根导出链。
2. **类型形态**：类型字段猜错 → 查依赖图符号档案的完整定义体，不凭记忆写签名。
3. **深链违规**：`use` 路径含殿/阁/园 → 改为经 lib 根或 Service Definition。
4. **跨维直调**：`use` 了对方维度的府 → 改为经鸿蒙事件总线/状态共享。

排查工具：依赖图 `查模块` / `查库根导出` / `查文件`，看真实签名再写。

### 7.2 落点被拒（涉及路径空）

写文档/配置/脚本类任务（产物非 `.rs`）被落点护栏拒绝：

- 涉及路径净化认合法产物扩展名表（.rs/.md/.json/.toml/.yaml/.yml/.txt/.py/.sh/.ps1/.bat/.html/.css/.js）。
- 传承殿（无源码）受源码维度白名单限制拒写，子系统文档写进对应府目录内，传承殿只放总索引。

### 7.3 空园残留

无源码的空目录（历史迁移遗留）会引诱误当落点：

- 空目录一律删除，不往空目录/非涉及路径写代码。
- 根目录严禁出现 `src/`、`tests/`、`scripts/` 空目录，发现立即删除。

### 7.4 日志混用

技术日志与业务流水混用：

- 技术日志（tracing）→ `rizhi_fu` lib 根。
- 业务流水（领域数据）→ 识海承载-府格位记录。
- 两者勿混，勿重复实现。

### 7.5 设计未入稿

实现溯不到设计稿源：

- 新增设计先入稿对应设计稿章节，再落码。
- 溯不到源视为补丁，需补入稿或说明缘由。

### 7.6 沙箱构建超时

验收阶段沙箱构建超时（当前已知问题，2026-08-21）：

- 现象：验收阶段在沙箱内 `cargo build` 超时未完成。
- 处置：正在修复，临时可放宽沙箱超时阈值或分步构建。
